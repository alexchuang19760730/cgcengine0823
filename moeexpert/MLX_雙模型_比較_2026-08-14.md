# MLX 雙模型比較：qwen36-35B-A3B vs gemma4-26B-A4B（M4 16GB）

日期：2026-08-14
環境：Apple M4、16GB unified memory、mlx-lm 0.31.3 / mlx 0.31.2、transformers 5.7.0
工具：`mlx_lm.benchmark -p 128 -g 128 -n 3`（qwen36 用 -p 128 -g 128、gemma4 用同參數）
Mio（github.com/Ruler-Dev/mio）已 clone 至 `temp/mio` 並安裝（`pip install -e . --no-deps`，import OK），MLX 推理走 mlx-lm。

## 實測結果

| 模型 | MLX 版本 | 檔案 | model_bytes | prefill tps | decode tps | peak RAM | 來源 |
|---|---|---|---|---|---|---|---|
| **qwen36-35B-A3B** | 2-bit affine g64 | 10.9GB | 10,346MB | **171.6** | **60.0** | 11.17GB | `shawon/Qwen3.6-35B-A3B-mlx-2Bit` |
| **gemma4-26B-A4B** | 2-bit affine g32 | 10.25GB | ~10GB | **225.8** | **37.5** | 10.01GB | `zecanard/gemma-4-26B-A4B-it-...-MLX-2bit-int2-affine`（uncensored-abliterix 變體） |

### 三方引擎對照（同機 M4 16GB）

| 引擎 | qwen36 decode | gemma4 decode | 備註 |
|---|---|---|---|
| **MLX（本次）** | **60.0 tok/s** | **37.5 tok/s** | 2-bit，peak ~10-11GB |
| llama.cpp | 25.5-27.9（IQ2_XXS Metal） | 16.3（IQ3_S 純 CPU；Metal OOM） | 前測 |
| Swift TurboFieldfare | 5.5-5.8 | 12.7 | 前測（含 expert streaming） |

**MLX decode 全面勝出**：qwen36 60 vs llama.cpp 27.9（2.2×）、gemma4 37.5 vs CPU 16.3（2.3×）、Swift 5.8 的 10×+。

## Metal working set 調查結論（已實測）

M4 `max_recommended_working_set_size` = **11,453MB**，是 MTLDevice 硬體建議值，**無公開 API 放大**：

| 嘗試 | 結果 |
|---|---|
| `mx.set_memory_limit()` | 預設已是 working set 1.5×（17.2GB），非限制來源，無效 |
| `mx.set_wired_limit()` | 拒絕設 > working set：`ValueError: Setting a wired limit larger than the maximum working set size is not allowed` |
| 14GB MLX 4-bit（gemma4-hf-snapshot-meta）decode | `kIOGPUCommandBufferCallbackErrorOutOfMemory` 硬崩 |
| 4.5bpw 13GB（convert 保留原 4-bit config）decode | Killed:9（系統 OOM） |
| CPU device 推論（14GB 4-bit） | 可跑但 >600s 才 8 tokens（等同 llama.cpp CPU 路徑） |

**16GB 機 MLX 可行區間**：模型 ≤ ~11GB 檔案（model_bytes ≤ working set）。qwen36 3-bit（16GB）OOM、4-bit（20GB）OOM → **2-bit 是唯一可行檔位**（與 llama.cpp IQ2 成功區間一致）。

## 下載過程踩坑（供復用）

1. **xet CDN 檔**（shawon/majentik/zecanard 等 repo）`curl -C -` 續傳**有效**（macOS 無 `timeout` 命令，之前誤判）；斷線會自動 retry，`until curl && size-check` 迴圈可推進。
2. huggingface_hub / hf CLI 對 hf-mirror 的 xet 檔 HEAD 檢查失敗（`does not seem to be on huggingface.co`）→ 改用純 curl。
3. **小 shard 陷阱**：最後一個 shard 常是 metadata/vision 小檔（如 qwen36 shard3 = 158MB 只有 lm_head 3 個 tensor、gemma4 shard3 = 263MB 含 vision），完成條件不能寫死大閾值，應比對 `model.safetensors.index.json` 的 tensor 數用 `safe_open` 驗證。
4. TurboQuant 版 gemma4-2bit（majentik）**mlx-lm 0.31.3 無法載入**（gate_proj shape 352 vs 704，特殊打包佈局）→ 改用 zecanard 標準 affine int2。
5. `mlx_lm.convert --q-bits 2` 對已含 quantization config 的模型會**保留原 config**（gemma4-hf-snapshot-meta 4-bit → 輸出 4.5bpw 13GB 仍 OOM），不會真的降到 2-bit。

## Mio / DFlash 結論

- Mio registry 支援 `qwen3.6-35b-a3b`（target + `z-lab/Qwen3.6-35B-A3B-DFlash` draft）。
- 但 **DFlash draft = 42.4GB（fp16 35B）**，16GB 機連 draft 都放不下，且 draft 全量載入同樣撞 working set 牆 → **Mio DFlash 在 16GB 機對 35B 不現實**。
- Mio 官方驗證場景是 M4 Max 48GB + Qwen3.6-27B（dense）+ 16GB draft。
- Mio 的 baseline AR 模式（無 draft）等同 mlx-lm，無額外收益。

## 2-bit 品質評估（coherence 樣本，2026-08-14）

以 `mlx_coherence.py`（自寫 decode 迴圈抓每步 logprob 向量 [V]）對兩模型各跑 code + prose 24 tok，檢查 logits 退化（NaN / 熵崩潰 / top-1 機率 / token 重複）：

| 模型 | 樣本 | NaN 步 | mean 熵 | min 熵 | mean top-1 p | tail12 unique | 文本 |
|---|---|---|---|---|---|---|---|
| **qwen36-2bit** | code | 0/24 | 2.26 | 0.39 | 0.53 | 3/12 | `# The 1st ... 6 6 4`（輕微重複） |
| **qwen36-2bit** | prose | 0/24 | 1.08 | 6e-07 | 0.71 | **12/12** | 「Here is the explanation, presented in three sentences: 1. The sky appears blue during the...」✅ 連貫 |
| **gemma4-int2** | code | 0/24 | 2.09 | 0.40 | 0.54 | 8/12 | `edverne:urverary:eduss1ed:ednt1`（亂碼） |
| **gemma4-int2** | prose | 0/24 | 1.25 | 0.06 | 0.67 | 7/12 | `1244444412345432f4s than2f3`（亂碼） |

### 結論

1. **兩模型 logits 都沒退化**（0 NaN、熵正常範圍、top-1 p 0.5-0.7）——2-bit 不造成數值崩潰。
2. **qwen36-2bit 品質可接受**：prose 連貫且多樣（tail12 unique 12/12）、輸出結構正確（編號 1. 2. 3.）；code 出現輕微重複迴圈（「6 6 4」）——這是 2-bit 在程式碼上的真實品質損失訊號。
3. **gemma4-int2 無法作為文字品質評估對象**：該 repo（zecanard）是 **VLM arch**（`Gemma4ForConditionalGeneration`、含 `vision_config` + 358 個 vision tensor、shard3 89 tensor 含 vision）——純文字推論輸出完全亂碼（bare 與 chat template 都一樣，tokenizer round-trip 正常 → 非 tokenizer 問題）。**先前對照表的 gemma4 37.5 tok/s 數字也是這個 VLM 模型跑 text-only 得到的，不可作為文字對比點**。
4. **社群沒有 gemma4 純文字 2-bit MLX**（搜尋確認：現有 MLX gemma4 只有 4-bit VLM 15.6GB、6-bit、VLM 轉換版）→ gemma4 的 MLX 公平對比需要自己轉：`google/gemma-4-26B-A4B`（base）用 `mlx_lm.convert --q-bits 2`（且不能有保留原 quant config 的陷阱），或直接改用 4-bit + offload 路線。

## 4-bit + offload vs 2-bit MLX 取捨（2026-08-14 實測）

**重要前提（兩點都先講清楚）：**

1. **C streamer 目前無法跑 decode**——`src/cgc_expert_compute.c`（128 行）只是「權重視圖橋接」（`compute_bridge_init / load_weights / get_tensor_info`），**沒有 dequant、沒有 GEMM、沒有 forward**。全 decode 需要 Swift 引擎的 Metal kernel 鏈。
2. **gemma4-hf-snapshot-meta（14GB）也是 VLM**（`Gemma4ForConditionalGeneration` + `vision_config`，與 zecanard int2 同 arch）→ 純文字推論同樣會亂碼，不能當文字品質來源。**我們生態系裡可用的 4-bit 文字版 gemma4 = .gturbo repack（gemma4-r4，13GB）**，由 Swift 引擎（= C streamer 要移植的那套 offload 架構）執行。

### 實測數據（同機 M4 16GB）

| 指標 | 4-bit + offload（Swift gemma4-r4） | 2-bit MLX（gemma4-int2） | 2-bit MLX（qwen36-2bit，有效 2-bit 參考） |
|---|---|---|---|
| decode tok/s | **17.1**（256 tok @ load 2.2；正典乾淨窗 19.8、128 tok 四輪中位 14.3） | 37.5（VLM，無效文字對比） | 60.0 |
| 峰值記憶體 | ~3-4GB resident（13GB 模型流式） | 10.01GB（10.25GB 整檔） | 11.17GB（10.9GB 整檔） |
| prose 品質 | ✅ 連貫且科學正確（Rayleigh 散射解釋正確） | ❌ 亂碼（`1244444412345432f4s`） | ✅ 連貫（tail12 unique 12/12） |
| code 品質 | ✅ 連貫分析（quicksort 複雜度/建議正確） | ❌ 亂碼（`edverne:urverary`） | ⚠️ 重複迴圈（「6 6 4」） |
| logits 退化 | —（引擎未暴露 per-step logits） | 0 NaN / 熵正常 | 0 NaN / 熵正常 |
| 記憶體餘裕 | **大**（剩 12-13GB 給系統/多工） | 小（free% ~0.5% 邊緣） | 小（11.17GB 逼近 11.45GB） |

### 取捨結論

1. **速度代價（修正後）1.9-3.5×**：2-bit 原生（37.5-60 tok/s）vs 4-bit+offload（**17.1-19.8 tok/s**，256 tok 乾淨窗實測；128 tok 中位 14.3）。**注意：最初 9.59 tok/s 是 load 2.6 髒窗的污染值**——正典 §13.15 乾淨窗 256 tok 19.8、README 官方 r4 21.5；本機實測 256 tok @ load 2.2 = 17.08。offload 的 IO + 流式調度成本換來**記憶體餘裕 12-13GB**（多工共存）與 **4-bit 全品質**，且 4-bit+offload 與 2-bit 的差距沒有一開始想的大。
2. **品質代價（2-bit）**：prose 保真但 code 出現重複迴圈（qwen36 實測）；gemma4 甚至沒有可用的 2-bit 文字版（VLM 或不存在）——所以 gemma4 家族內其實沒有「2-bit vs 4-bit」的公平對比，只有 qwen36-2bit（60 tok/s）vs gemma4-r4（17-19.8 tok/s）的跨家族對比。
3. **本機最佳配置取決於用途**：
   - 要速度 + 品質可接受的通用對話 → **2-bit MLX qwen36（60 tok/s）**；
   - 要 code 品質 + 多工共存（server 常駐）→ **4-bit + offload（17-19.8 tok/s，剩 12GB 餘裕）**——修正後差距縮到 1.9-3.5×，offload 的價值比初始判斷高；
   - gemma4 的 MLX 2-bit 路線要公平對比需自行轉 base text-only（現無現成）。
4. **C streamer 的價值定位不變**：它把 Swift 的 offload 架構搬進 C/llama.cpp 生態（P1-P3 尚未實作 compute），完成後才有「4-bit + offload」的跨平台版本。現階段 4-bit+offload 的速度/品質參考 = Swift 引擎實測值。

## 決策（2026-08-14）：MLX 路線暫緩，focus = llama.cpp

**單考慮 llama.cpp backend，暫時不考慮移植到 MLX。** 理由（本文件實測數據）：

1. MLX 沒有 per-expert offload → 4-bit gemma4（14GB）必然 OOM，唯一能跑的 2-bit 是 VLM 亂碼 → **MLX 在 16GB 機對 gemma4 沒有品質可用路徑**。
2. llama.cpp kernel 效率已實證（qwen36 IQ2 Metal 27.9 tok/s 是 Swift 5.8 的 4.8×）——只要塞得進 working set，llama.cpp 就是最快。
3. gemma4 塞不進（11.29GB > 11.45GB）正是要解的題 → **expert bounded residency fork**（LLAMACPP_EXPERT_BOUNDED_RESIDENCY_FORK_方案 P1）是唯一能把「llama.cpp kernel 效率 + offload 記憶體彈性」合併的路。
4. 本文件的 2-bit MLX 數據保留作「更小 quant 基線」參考（fork 方案 §5.2 的 A/B 對照組）。

## 建議

1. **16GB 機 MLX 最優路徑 = 2-bit 原生**（本表數據），不需要 Mio 的 DFlash 複雜度。
2. 若要保 4-bit 品質（gemma4-hf-snapshot-meta 14GB）→ 走 **expert-wise offload**（pread + 匿名 slot + zero-copy per-expert mul_mat，即 TurboFieldfare/C streamer 既有架構），MLX 原生做不到 per-expert 流式。
3. 2-bit 與 4-bit+offload 可做 A/B（吞吐 vs 品質）。
