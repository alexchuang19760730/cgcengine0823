1. 核心問題：cgc engine 有沒有參與轉換？

沒有。整條 GGUF → .ms 轉換鏈是 PC 端離線轉換，與 cgc engine（llama.cpp 裝置端推理引擎）完全無關。
  • cgc engine：裝置端的推理引擎（llama.cpp via N-API），只負責執行 GGUF 模型，不參與任何模型格式轉換。
  • 轉換工具：MindSpore 官方離線工具 converter_lite（本地執行檔，非雲端 API）＋ 我們自寫的 Python 圖處理腳本（transformers / torch.onnx / onnx 圖手術）。

5. 已知限制與設計決策

  • x86 fp16 限制：MindSpore NNACL 在 x86 上把 fp16 活動值自動轉 f32、權重留 f16 → ARITHMETIC_DATA_TYPE_UNMATCH（error 18）。因此 PC 驗證用 fp32 版；fp16 .ms 留給 ARM 裝置（NNACL ARM 有完整 fp16 kernel）。
  • 無 KV cache：匯出時 use_cache=False、固定 shape 1×128。此為「單次 prefill 基準」型模型，裝置端要做自回歸生成需在 runtime 端逐 step 餵入（後續可評估匯出帶 cache 的版本或以 reshape 支援動態長度）。
  • 精度基準：ref 為 fp16-ORT logits，fp32 版差異 max≈1.09 / mean≈0.13 / cosine 0.9994，屬 f16↔f32 計算精度差，argmax 一致。
  • 磁碟策略：C: 空間不足 → 大檔（fp32 資料 3 GB、.msw）全部寫 D:\ms_convert_fp32\；fp16 產物備份 D:\ms_convert_backup\。

  • MS Lite 的獨特價值是它自己的 delegate 生態（HarmonyOS 裝置可接 NPU）——這是 llama.cpp 沒有的。
  • 最務實的整合在 App 層而非 runtime 層：GenerationWorkflow 統一介面，依模型格式路由到 cgc engine（GGUF）或 MS runtime（.ms），兩引擎並存、互相基準。

9.2 風險與對策

  • 執行緒爭搶：MS 與 ggml 都想吃滿 CPU → 對策：MS context threads 設低、ggml 端獨佔大核；或按層序列化交替執行。
  • 記憶體交接：邊界 tensor 需零拷貝（MS tensor data ptr 直接餵 ggml）→ 兩邊都是 C++ 連續記憶體，可行。
  • router 歸屬：router 本身極小（H×N gemm + topk），放 MS 端即可；top-k 結果以 int32 張量過邊界。
  • 模型適配：僅 MoE 模型（35B-A3B）受益；0.6B dense 無專家，走純 MS 路徑做管線驗證正好互補。

9.3 KV cache 關卡：膠囊邊界 + pad-to-4 設計（2026-08-29 補充）

問題本質：KV cache 是「三重動態」，MS 凍結圖一重都容不下。
動態物decode 每步怎麼動MS 靜態圖的下場
KV cache 本體[T, kv_heads, dim]，T 每步 +1（MTP verify 時 +3）——跨步持續存在的狀態 形狀編譯期定死；更致命的是 Predict() 無狀態，沒有「buffer 活過這次調用」的概念
causal mask形狀 [B, T+1] 每步變 0.6B 管線用 export_baked.py 把 mask 烘焙成常數——只在固定 1×128 單次 prefill 成立，decode 第一步就失效
RoPE position絕對位置每步位移，MTP verify 跳位位置值是 runtime 資料，非圖常數

llama.cpp 沒這個問題是因為它每個 decode step 重建計算圖（動態圖天生處理動態形狀）——兩引擎的根本性格差異，KV cache 是衝突爆發點。

解法核心（本設計最重要的一句話）：
KV cache 不過邊界、不進 MS 圖——它作為 C++ 物件住在 custom op 內部，跨 Predict() 調用持續存在。
MS scheduler 每步調用 AttnWithKV custom op 時，op 內部直接讀寫自己持有的 KV buffer （ggml 端用 llama.cpp 現成 kv-cache-unified 機制）。MS 以為在調無狀態算子， 實際每個 op 實例是有記憶的膠囊——動態狀態就這樣走私過凍結圖的邊界。
反例（不可行）：KV 當 input/output 每步過邊界——ctx 2048 全模型 KV ≈350MB，每步 copy 進+出 700MB， 在 ~40GB/s 頻寬 = 17ms/step 純搬運 = KV 讀取成本付兩次。膠囊方案成本為零。
每層切點（decode batch pad 到 4） MS piece 1 residual add + RMSNorm + QKV proj （靜態 [4,2048] 恆定） │ 邊界：q,k,v [4,2048] + position + real_len [CGC op A] AttnWithKV：RoPE + KV 寫入 + attention （動態三件套全在此） │ 邊界：attn_out [4,2048] MS piece 2 O proj + residual + RMSNorm + router + shared expert │ 邊界：hidden [4,2048] + topk ids [4,8] int32 + routing weights [CGC op B] MoEExpertFFN：routed experts + 加權合 （data-dependent 路由 + GGUF 量化權重） │ 邊界：moe_out [4,2048] MS piece 3 = 下一層 piece 1 ... 鐵律：形狀會變的、有狀態的、依賴 runtime 資料的 → cgc 側； 形狀恆定的純矩陣運算 → MS 側（讓 MS GPU backend 餵 Maleoon）

9.3.1 O projection 旋鈕（政策決定，非技術決定）

O proj 放 cgc op A 內O proj 留 MS piece 2 開頭
邊界數/層23（attention 輸出先過回 MS）
誰算ggml/CPUMaleoon（經 MS GPU backend）
適用MS GPU 慢或不可用時的 fallbackMS GPU 快時——dense 算力盡量外包

第三邊界成本 μs 級（activation 4×2048×4B ≈ 32KB）。Maleoon compute 吞吐實測後決定撥向。

9.3.2 batch 動態 → pad-to-4 + cgc 側 mask = 全靜態圖

  • MTP 三種 decode batch（target 1 / draft 2 / verify 3）→ MS 圖固定 pad 到 4。
  • dense matmul / RMSNorm / router 逐列獨立：pad 的垃圾列不影響真實列數值（真實 token 的 bit-identity 保持）。
  • 垃圾列由 cgc op A 的 mask 兜底——attention 直接遮掉、KV 只寫真實位置、sampling 只看真實列。
  • 紅利：MS 側永遠不需要動態 mask，圖完全凍結。4×2048 GEMM pad 開銷可忽略。

9.3.3 排程順序與未知數

  • prefill 先不走 MS：一次性成本，chunked prefill 圖更大——直接 cgc 純 CPU；MS 混合先只做 decode（效能關鍵路徑）。之後若要 GPU prefill：另導 b=128 的 .ms 變體，dense 權重（~1GB）兩份，屆時再評估。
  • 未知數 1：MS Lite 2.4 custom kernel 調用是序列還是可並行、與 MS backend 的執行緒爭搶（第一個實測點）。
  • 未知數 2：MS GPU backend 在 Maleoon 的實際吞吐——決定 O proj 旋鈕方向。
  • 未知數 3：registry/register_kernel.h 註冊的 op 能否持有跨調用狀態（C++ 物件成員，理論可行，需驗證生命週期）。
