§1 摘要

b23fb51 的 ngl 99 + expert-cache 在 decode 時產生 garbage output，速度達 25 t/s 但輸出無用。根因是 graph_get_cb 的 pool repoint 邏輯把 compute tensor 的 data 指向 pool region，導致 gate logits/FFN 數據損壞。修復只需 ~30 行：修 cgc_done counter + 把 remap 寫入從 submit 之後挪到 submit 之前。

輸出品質❌ Garbage（"!!!..."）✅ Correct（bit-identical to base）
Decode speed25.5 t/s~25 t/s（sync overhead <2%）
改動量—~30 行 C++（ggml-backend.cpp）
Pool hit rate98.7%98.7%（不變）

關鍵認知：問題不是 "callback timing race"（白皮書 v1 的錯誤假設），而是 graph_get_cb 的 repoint 邏輯本身有 bug——它把 compute tensor（ffn[0]）的 data 指向 pool region，導致 Metal 讀到垃圾。修復方向是修正 repoint 邏輯 + 保證 callback 在 submit 前完成 remap 寫入。

§2 根因分析

問題比 v1 描述的更深：不是 "pool 空導致 decode garbage"，而是 prefill 階段 il=2+ 就已經壞了，且在 sequential 路徑（無 CGC_OA_ASYNC、每段都 synchronize）下同樣復現。

2.2 根因鏈：graph_get_cb repoint bug

═══ graph_get_cb 的 repoint 邏輯（llama-context.cpp:2789-2808）═══ 當 ffn_moe_topk_remap 被建立時，repoint ALL 4 kinds 的 src0 到 pool： ffn[0] = ffn_moe_gate 的 src0 → pool kind-0 region ffn[1] = ffn_moe_up 的 src0 → pool kind-1 region ffn[2] = ffn_moe_down 的 src0 → pool kind-2 region ffn[3] = ffn_moe_gate_up 的 src0 → pool kind-3 region ═══ Fused-down 路徑下的問題 ═══ Fused-down 把 gate+up 合併成一個 mul_mat_id 計算： gate_up = mul_mat_id(gate_up_exps, cur, ids) ← compute tensor（結果） gate = view_3d(gate_up, [0..n_ff]) ← ffn_moe_gate up = view_3d(gate_up, [n_ff..2*n_ff]) ← ffn_moe_up 關鍵：ffn_moe_gate 的 src0 = gate_up（compute tensor） ffn[0] 被 capture 為 gate_up 的 data pointer repoint 把 ffn[0]->data 改指向 pool kind-0 region 結果：gate_up（compute tensor）的 data 被改指向 pool region Metal 執行 gate_up mul_mat_id 時，寫入目標變成 pool region 下游的 gate view 和 up view 讀到 pool region 的垃圾數據 → gate logits NaN → probs NaN → garbage output
Why il=0 is correct but il=2+ is broken

L4_SKIP_LAYER0：layer 0 的 expert tensors 被排除在 pool 之外（il=0 無 pool region）。所以 ffn[0] 的 repoint 目標是 nullptr，repoint 不生效，gate_up 保持原始 data pointer → 正確。

il=1：可能因為 pool region 恰好與原始 buffer 重疊或 gate_up 的 compute 結果尚未被覆蓋，暫時正確。

il=2+：pool region 是獨立分配的記憶體，repoint 把 gate_up 的 data 指向 pool → Metal 寫入 pool → 下游讀到垃圾 → NaN。

2.4 Prefill vs Decode 的差異

Prefill（n_tokens > 1）：不建立 remap leaf（n_tokens == 1 check 失敗），但 graph_get_cb 仍然在 ffn_moe_topk_remap 建立時 repoint——等等，prefill 不建立 remap leaf，所以 ffn_moe_topk_remap 根本不會被建立，repoint 不會觸發。

但實測 prefill il=2+ 就壞了。這意味著：

  1. Prefill 的 graph 結構與 decode 不同（n_tokens > 1），但仍然有某個機制導致 il=2+ 數據損壞
  2. 或者 prefill 的 garbage 是來自 上一個 decode step 的殘留 repoint（graph reuse）——但首次 prefill 不應該有殘留
  3. 需要 決定性 diagnostic：在 prefill 期間 dump layer2 的 gate logits（是 NaN 還是 ramp）和 layer1 的 FFN 輸出，定位是 gate 壞還是 FFN 輸出壞
待驗證假設

假設 A：prefill 的 garbage 不是來自 repoint（因為 remap leaf 不建立），而是來自其他機制（例如 graph reuse 殘留、或 prefill graph 結構本身的 bug）。

假設 B：prefill 的 garbage 是來自之前的 decode step 的 repoint 殘留（但首次 prefill 不應該有）。

假設 C：prefill 的 "identity routing" 是正常的（n_tokens > 1 時 topk 行為不同），不是 bug。

下一步：跑 diagnostic 確認哪個假設正確。

2.5 Segmented Dispatch 時序分析

═══ 現有 segmented dispatch（b23fb51 CGC_OA_ASYNC）═══ segment 分割：以 ffn_moe_topk 節點為邊界 seg[0] = [nodes 0 .. topk_0] ← layer 0 的 gate + topk seg[1] = [topk_0+1 .. topk_1] ← layer 0 的 FFN + layer 1 的 gate + topk seg[2] = [topk_1+1 .. topk_2] ← layer 1 的 FFN + layer 2 的 gate + topk ... seg[40] = [topk_39+1 .. end] ← layer 39 的 FFN + output Submit-ahead 時序： submit seg[0] → submit seg[1] ahead → wait seg[0] → callback (writes remap_0) → wait seg[1] → callback (writes remap_1) → ... 問題 1：submit seg[1] 在 callback 寫 remap_0 之前 Metal 在 seg[0] 完成後立即開始 seg[1] seg[1] 包含 layer 0 的 FFN（讀 remap_0） 但 callback 還沒 fire → remap_0 是上一步的舊數據 問題 2：cgc_done counter 只掛 main command buffer 但每個 segment 有 n_cb=8 個 command buffer done0+i+1 可能在 tail buffer 未完成時就滿足 → callback 讀到不完整的數據 ═══ Sequential 路徑（無 CGC_OA_ASYNC）═══ 每個 node 都 synchronize + callback： submit node[i] → synchronize → callback (writes remap) 這消除了 timing race，但 prefill il=2+ 仍然壞 → 證明根因不是 timing race，而是 repoint 邏輯本身

關鍵結論：sequential 路徑消除了所有 timing race（每步都 synchronize），但 prefill il=2+ 仍然壞。這證明根因是 graph_get_cb 的 repoint 邏輯把 compute tensor 指向 pool，不是 callback 時序問題。修復方向是修正 repoint 邏輯，不是改 segmented dispatch 時序。

§3 修復方案（v2：最小改動）

基於 §2 的根因分析，修復只需兩個改動：(1) 修正 cgc_done counter、(2) 把 remap 寫入從 submit 之後挪到 submit 之前。不需要 per-layer two-phase segments、不需要禁用 fused-down、不需要 CPU argsort。

3.1 Fix 1：cgc_done counter（~10 行）

問題：cgc_done counter 掛在 main command buffer 的 addCompletedHandler 上，但每個 segment 有 n_cb=8 個 command buffer（CGC_N_CB=8）。done0+i+1 可能在 tail buffer 未完成時就滿足。

修復：只在 segment 的 最後一個 command buffer（main buffer）上掛 counter，確保 counter 只在 segment 完全完成時才遞增。

// ggml-metal-context.m: 在 cmd_bufs[n_cb]（main buffer）上掛 counter
// 而不是在所有 buffer 上都掛
if (cmd_buf_idx == n_cb) {  // main buffer
    [cmd_buf addCompletedHandler:^(id<MTLCommandBuffer> cb) {
        atomic_fetch_add(&ctx->cgc_done, 1);
    }];
}

3.2 Fix 2：Remap 寫入提前（~20 行）

問題：現有時序是 submit seg[i+1] → wait seg[i] → callback（寫 remap_i）。seg[i+1] 在 callback 之前就已 submit，Metal 在 seg[i] 完成後立即開始 seg[i+1]，但 remap_i 還沒寫入。

修復：改為 wait seg[i] → callback（寫 remap_i）→ submit seg[i+1]。Remap 在 submit 之前就緒。

// ggml-backend.cpp: segmented dispatch loop
for (int i = 0; i < n_segs; i++) {
    // 1. Wait for seg[i] to complete
    while (cgc_done(split_backend) < done0 + i + 1) {
        sched_yield();
    }
    // 2. Fire callback (writes remap_i)
    if (!sched->callback_eval(ttopk, false, sched->callback_eval_user_data)) {
        break;
    }
    // 3. NOW submit seg[i+1] (remap_i is ready)
    if (i + 1 < n_segs) {
        struct ggml_cgraph gv = seg_view(i + 1);
        ec = ggml_backend_graph_compute_async(split_backend, &gv);
    }
}

關於 GPU argsort

GPU argsort（ggml_argsort_top_k）在同步正確後是可靠的。v1 白皮書聲稱 "buffer aliasing 使其不可靠" 是錯誤的——實測的差異是 async race（提前讀），不是 static aliasing。修好 cgc_done counter + remap 提前後，GPU argsort 輸出的 I32 IDs 是正確的，callback 可以直接讀取 t->data。

不需要切到 CPU argsort（從 probs 讀取 1KB + 256 元素 sort）。保留 GPU argsort 是更簡單且更快的方案。

§4 設計決策

4.1 Routing 來源：保留 GPU argsort

方案優缺點決定
A. 保留 GPU argsort 零額外 CPU 開銷、sync 正確後可靠（32 bytes read） ✅ 採用
B. CPU argsort from GPU probs 避免 buffer aliasing（但 aliasing 是 async race 非 static） ❌ 不需要（多此一舉）
C. CPU gate matmul 完全不依賴 GPU（但 IQ3_XXS 反量化 ~2s/step） ❌ 不可行

4.2 Submit-ahead vs Sequential

Phase 1：Sequential（推薦先做）Phase 2：Event Gate（之後優化）
時序 wait seg[i] → callback → submit seg[i+1] submit seg[i+1] ahead + event gate（GPU wait pool ready）
GPU 利用率 ~98%（GPU 在 callback 期間空轉 ~18µs/segment） ~100%（GPU 透過 event gate 自行等待）
速度 ~25 t/s（-2%） ~25.3 t/s（-0.8%）
複雜度 低（~30 行） 高（~100 行 + Metal event）
風險 低 中（event sync edge case）

4.3 Pool Capacity Overflow

問題：pool_capacity（~174 slots/layer）可能 < n_experts（256）。如果 union 超過 pool 容量怎麼辦？

已有機制：callback 中的 uni.size() <= n_slots 判斷。union 超限時走 L3-B gather 路徑（在 callback 中 gather 所需 experts 到 contiguous buffer）。不需要額外的 clamp 或 fallback。

⚠️ 不要加 clamp expert IDs 到 pool_capacity-1——這會選到錯誤 expert，導致 garbage。

4.4 Fused-Down

Fused-down（CGC_GLU_FUSED_DOWN=1）把 gate+up 合併成一個 mul_mat_id。repoint 到 pool 是正確且必要的——問題不是 fused-down 本身，而是 repoint 的 target 選錯了（把 compute tensor 的 data 指向 pool）。

修復 repoint 邏輯後，fused-down 可以正常工作。不需要禁用。

4.5 Prefill Pool Loading

Callback 在 n_tokens > 1 時只 record_routes()，不 ensure_batch()。Pool 在 prefill 期間保持為空。

影響：第一個 decode step 的 pool 是 cold 的（~5% miss rate → ~500µs I/O tail）。但 prefill 只執行一次，不影響 steady-state decode throughput。

可選優化：在 prefill callback 中也呼叫 ensure_batch，讓 pool 在 prefill 結束時已 warm。這會增加 prefill 時間 ~5-50ms，但改善第一個 decode step 的 latency。
