三、pre-commit 覆蓋情況

重點不是另起一支測試腳本，而是把 runtime 驗收收回 scripts/check_build_tracked.sh 裡。這樣 build 追蹤、死鎖防護、原始碼↔binary 同步、以及 short/long prompt no-0000 驗收都在同一入口。

層級項目位置預設本輪狀態
T-P1~T-P5dylib / symlink / exe / rpath 追蹤scripts/check_build_tracked.sh自動PASS
T-P6main⊆dev 分支包含性scripts/check_build_tracked.sh自動PASS
T-P7hist-prefetch 死鎖靜態守衛scripts/check_build_tracked.sh自動PASS
T-P8原始碼↔binary 同步scripts/check_build_tracked.sh自動PASS（含 libllama-cli-impl.dylib 追蹤）
T-P9重型生產驗收：short_base 無 0000 + 命中 Parisscripts/check_build_tracked.shRUN_CGC_PROD_ACCEPT=1PASS
T-P10重型生產驗收：long_base / long_dense 無 0000 + 指標摘錄scripts/check_build_tracked.shRUN_CGC_PROD_ACCEPT=1PASS

為什麼 T-P9/T-P10 是條件啟用：它們是 35B production 模型的重型驗收，單次要數分鐘。如果做成每次普通 commit 都強制執行，會把 pre-commit 變成「幾分鐘起跳」的超重流程，開發體驗和誤判風險都不好。現在的做法是：腳本內已覆蓋，但以 RUN_CGC_PROD_ACCEPT=1 顯式開啟；需要速度門檻時，可再加 CGC_ACCEPT_SHORT_MIN_TPS / CGC_ACCEPT_LONG_BASE_MIN_TPS / CGC_ACCEPT_LONG_DENSE_MIN_TPS。

手動重跑本輪同口徑驗收：
BIN_DIR=src/llama.cpp/build/bin RUN_CGC_PROD_ACCEPT=1 \
  scripts/check_build_tracked.sh

可選：把 decode 速度也變成 gate
CGC_ACCEPT_SHORT_MIN_TPS=12
CGC_ACCEPT_LONG_BASE_MIN_TPS=24
CGC_ACCEPT_LONG_DENSE_MIN_TPS=21
