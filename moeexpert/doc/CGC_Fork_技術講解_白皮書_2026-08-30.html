§3 Bit-Identical：位元級一致的三支柱

定義：同 prompt、同 seed、greedy（temp 0）下，投機（MTP）輸出 = 非投機（llama-simple）輸出，逐 bit。這不是「結果相似」，是同一 token 流。達成需要三個獨立污染源同時關閉 —— 缺一個都會在幾百個 expert-ID key 上翻轉。

3.1 支柱一：M-invariant kernel 選擇（CGC_MM_BITIDENT）

問題：small-batch mat-mv family 的 (nxpsg, r1ptg) 由 ne11（=M） 選擇 → per-row K-reduction tree 隨 batch 大小改變： M=1（simple 逐 token） → kernel A 的歸約樹 M=3（spec verify 批） → kernel B 的歸約樹 同一邏輯列在不同 M 下 ULP 不同 → logit 漂移 → argsort 近平手翻轉 修復：CGC_MM_BITIDENT=1 → 所有 src[0] 型別 ne11<=8 都繞過 small-batch family 落到 mul_mv。 mul_mv 的 per-element 映射只依 (tsrc0, ne00)；ne11 只設定 grid 列數 → 每列結果 M-invariant： prefill 尾 M=2 / verify M=3 / decode M=1 全部位元組一致 v2 教訓：v1 只繞 F32xF32 → UD 動態量化讓 shared-expert/GDN 投影出現 Q8_0，第一個 flip 藏在 layer 4 → v2 擴到所有型別 代價：M∈[2,8] 失去 small-batch GEMV（回退 mul_mv）—— 這是「品質優先」開關，追求速度可不設

3.2 支柱二：warmup / probe 污染排除

spec 路徑在 prefill chunk 0 之前偷偷跑了兩次 decode，兩次都會填 expert slot + bump LRU tick，而 llama_memory_clear 不會重置 expert cache → spec 的 pool 狀態與 cold-cache 的 simple 從第一步就分歧（chunk0 L4 rows 0-2 專家翻轉的根因）：

污染源是什麼關閉選項
手動 warmupspec 初始化時的 2-token warmup decode（還以錯誤的 graph topology 建圖）CGC_MTP_NO_WARMUP=1
seq-rm probecommon_context_can_seq_rm(ctx_tgt) 探測 decode 的 [0,0] 2 tokensCGC_NO_SEQ_RM_PROBE=1

兩者皆 env-gated（預設執行 = upstream 行為）。CGC_DECODE_TRACE 是抓這類隱藏 decode 的工具：每次 decode 印 ctx/type/n_tokens/pos0 —— MTP 位元調查就是靠它看到「看不到的 2-token warmup」。

3.3 支柱三：galloc lifetime-overlap guard（無選項，永久生效）

最隱蔽的一個：fused gate+up+swiglu kernel 在 GATE 節點位置寫 swiglu 輸出 c，但 galloc 按 SWIGLU 位置分配 c 的記憶體 —— 若兩節點之間有張量（計算或讀取）與 c 重疊，fused 執行會覆寫它（量測：simple 圖形 777/800 keys 發散，galloc 把 y 的 freed range 重用給 c；spec 圖形 0/422 恰好無 overlap）。修復在 fuse 決策點檢查 idx+2..glu 每個節點的 dst 與 src 是否與 c 的記憶體區間相交，命中即拒絕融合 fallback 原路。純邏輯、無 env、安全層仍融合（decode 127.77 vs 145.10 ms/tok，快 12%）。

3.4 驗收方法（任何平台適用）

# 判定三件套（詳見 bit-identical 白皮書 §5）：
# 1) simp 16-token 續寫 == spec 續寫的精確前綴（byte-level）
# 2) accept rate = 12/12（此基準 prompt）
# 3) 兩 run 的 CGC-IDS 行同 (pmax,il) key 逐行比 → 0 差異
# IDS layout: [n_expert_used, n_tokens]，token row j = ids[j*n_used..]

§4 沒 Loop 沒退化：穩定性與品質防線

「沒 loop」= 不死鎖、不停滯（Metal completion wedge / dispatch 卡死）；「沒退化」= 輸出不變 garbage、不 "The The The"。兩者各有獨立防線。

4.1 死鎖防線（沒 loop）

層機制選項行為
偵測Metal watchdog：500ms dispatch timer，expected > done 停滯超閾值或 encode worker 卡住 → 判 stalledCGC_WATCHDOG=1、CGC_WATCHDOG_MS（預設 10000）dump 狀態 + probe
鑑別liveness probe：同 queue 與 fresh queue 各提交 3s probe bufferCGC_WATCHDOG_CAPTURE=1（另存 ioreg/memory_pressure/sample 到 /tmp）same-queue DEAD = 共享 command queue 從卡點全 wedged；fresh-queue DEAD = device/kernel 級 wedge —— 直接分層定責
止損停滯滿 60s（sampling grace）→ GGML_ABORT，恢復時 re-arm同上不無限掛死
緩解週期性全佇列 drain（waitUntilCompleted 於最後 buffer；FIFO 等於等全部）CGC_DRAIN_EVERY=K（0=off）假說：driver 的「從不排空 firehose」（~1900 cb/s 數分鐘）累積 wedge；週期靜默窗口讓 queue 完全回收。代價 = 每 K 段一個 2-5ms pipeline bubble
根除race-free 提交順序（預設）：hook 寫完 remap 之後才提交消費它的 command buffer不設 CGC_SUBMIT_AHEAD在 flight command buffer 的 buffer 上寫入是 UB（stale remap → 非確定性輸出）。舊 race 序僅留作 A/B
絕對不要設的兩個「重現 bug」開關
CGC_SUBMIT_AHEAD=1（回復 race 提交順序）與 CGC_TOPK_BOUNDARY=1（回退用 top-k VIEW 當 segment 邊界 —— view 是無依賴別名、可能排在生產者之前，用它當邊界會在 ids 算出前觸發 hook → 垃圾路由）。兩者都是刻意保留的 bug 重現器，做 A/B 對照用，任何生產 env 出現它們都是事故。

4.2 品質防線（沒退化）

退化形態根因防線
輸出亂碼BLAS（Accelerate）對 IQ3_XXS/IQ2_S 的 dequant 路徑build 期 flag 紀律：GGML_BLAS=OFF、GGML_ACCELERATE=OFF（GGML_CPU_REPACK=OFF 防 tensor 邊界）
"The The The" 式退化pool 滿 + 路由重尾：routed cold experts 全落 ZERO/未映射pin 策略（WIN_PIN/PIN_PROFILE）+ LAYER_CAPS 依 ROUTE_DUMP 分配 + prewarm；歷史 root cause 文件有完整翻案
MTP accept 崩潰verify fast path 的 cold 專家零貢獻不是隱藏而是量化：fast-path 遙測分項（n_fast_cold 等）量出 cold ~65% 為結構性 churn（per-layer working set >> slots），決策有數據

§5 Exact Cache：專家快取的位元組等同

「Exact」的承諾：池裡的權重 bytes 與直接從 GGUF 讀完全相同 —— 快取只改變「何時讀、用什麼 syscall 讀」，不改變讀到的內容。所有 IO 優化都遵守這條線。

5.1 快取單元與結構

單元 = (layer, expert) slot blob 內按 L1 index 順序串接該 expert 所有 present kind （gate/up/down 或合併 gate_up）的 segment， 每段以 pread 從 GGUF 絕對偏移讀入 （segment-aware addressing；與 gguf-py 在 qwen36 IQ2 + gemma4 IQ3 上 byte-verified） slot_table[layer*n_expert + expert] = slot idx（-1 = 非 resident） 配套：slot_owner / last_use(LRU) / queued / loading / pinned / pinned_static per-layer: slots_l（LAYER_CAPS 可各自不同）+ ZERO slot 保留位

5.2 替換策略：LRU + 三層 pin 偏好

策略選項解決的量測問題
基礎 LRU（預設）位元組等同 base
滾動 window pinLLAMA_EXPERT_CACHE_WIN_PIN=Kmiss 剖析：12291 miss 多為 REPEAT —— 熱專家在兩次使用間被 LRU 逐出。保留最近 K 個 batch union，成員標 pinned 免逐出。同步路徑、不寫 pool bytes → 無 race
靜態 pin profileLLAMA_EXPERT_CACHE_PIN_PROFILE=<file>離線 ROUTE_DUMP 產出的 per-layer top-N 清單，載入時標 pinned_static（永不解 pin；overflow 讓位）

pin 是偏好不是保留：pick_slot 三 pass（跳 pin → 可逐動態 pin → 可逐 LRU 靜態 pin）。全部跳過會留下 table==-1 → strict remap 讀 OOB → NaN 級聯；等待會死鎖。所以寧可逐出也不卡死。

5.3 IO 引擎（exact 的載體）

技術機制量測回退開關
持久 pread worker poolLLAMA_EXPERT_CACHE_WORKERS（預設 8，clamp 1..64，USER_INITIATED QoS）一 job = 一 segment pread，整層 miss 攤平一次提交、等 outstanding==0background QoS 會在重 compute 期間被餓死 —— 註解明言等待反而比同步 pread 慢LLAMA_EXPERT_CACHE_SERIAL_FILL
merge-read批次 segment 按 (file_idx, offset) 排序，檔案連續 run 合併為單一 preadv（記憶體端散落、檔案端連續 = iovec 語意）25470 次 90KB 散讀 → 少數大循序讀（2.3GB @ 3.2GB/s）LLAMA_EXPERT_CACHE_NO_MERGE
F_RDADVISE提交時對整批範圍發 Darwin 非同步 page-cache 預熱—LLAMA_EXPERT_CACHE_NO_RDADVISE

三者都保證 pool bytes 位元組等同（只改 syscall 模式）。這是「exact cache」的技術含義。

5.4 Hook 管線與正確性細節

  • snapshot ids：hook 先複製 top-k ids —— CGC_OA_ASYNC 管線下 galloc 可能重用 top-k buffer，不 snapshot 會 use-after-clobber。
  • 邊界用 argsort 不用 top-k VIEW：view 無依賴、可能排前 → 舊 bug（見 §4.1 紅框）。
  • drain_layer：丟棄該層未開始的 queued fill 並等 in-flight 完成 —— Metal region copy 是全 region 的，in-flight 填寫會撕裂。
  • prefetch 只用 free slot：free 用盡才逐該層 global LRU（當前步 union 剛 bump 過，LRU 必非 union → 誤逐出不會把當前命中變 miss）。
  • 大 prefill 批只記錄不 remap：routing 頻率進 prewarm 的依據。
  • 遙測分帳：prewarm 另計（否則命中率低估 ~15pt：81.3% vs 96%）；decode/pool 與 gather 分開；MTP verify/draft cold 分開。

5.5 靜態 pin profile：嚴謹品質判定與更新程序

PIN_PROFILE 是唯一「離線校準 → 線上釘選」的循環機制。以下判定基於 2026-08-30 實測（qwen36, n=64, 4GiB cache, K≈87/層, 256 experts/層）。

維度判定證據 / 機制
路由質量涵蓋優（2.6× baseline）coverage mean=87.8% min=80.8% max=93.1%；uniform baseline = K/256 ≈ 34% → 重尾路由確證，placement 槓桿有效
位元級安全性優（exact 模式）pin 只改「哪個 slot 放哪個 expert」與逐出順序；exact 路徑每個被路由 expert 都會被 ensure_batch 精確填充 → PIN_PROFILE 開/關輸出位元級相同（只有命中/miss 的時間差）。可用四方對比直接驗證
fast-path 品質影響條件性VERIFY/DRAFT fast path 下 cold expert 讀 ZERO slot（權重貢獻歸零）→ pin 減少 cold = 提升輸出品質。此模式下 pin 有品質後果（正向），與 exact 模式不同
死鎖/NaN 安全優pick_slot pass-2：槽滿且只剩 pinned 時靜態 pin 讓位（清 flag、記 n_pin_yield）—— 不卡死、不留 table==-1（NaN 級聯的替代方案）
workload 特異性最大弱點top-K 成員跨配置重疊僅 ~29%（不同 K/prompt 樣本）。校準 prompt 的路由分佈 ≠ 生產 prompt → 換 workload 必須重校準，否則 pin 保護的是錯的「熱」集
硬體 K 耦合需注意K = usable_slots = f(CGC_EXPERT_CACHE_BYTES, LAYER_CAPS)。大 cache 機器產的 profile（N 大）拿到小 cache 機器：多餘 id 不會炸（只在實際填入時標 pin），但 pin 密度稀釋；反向則覆蓋不足
模型錯配防護僅範圍檢查id 只驗 [0, n_expert) —— 錯模型 id 在範圍內靜默接受（語意錯誤的 pin，浪費保護不會崩潰）。依賴紀律：profile 檔名綁模型（qwen36_calib.pin）
懶標記中性pin 在 expert 首次被路由填入時才生效（非載入即 pin）→ 載入零額外成本，但也代表 profile 前幾個 step 逐漸生效

§6 L4 Skip-Load：Metal 零拷貝池

「skip-load」= 專家權重不在模型載入時全量進 Metal，只預留 capacity 大小的 pool region；池的 storage 就是 expert tensor 自己的 Metal buffer（收養而非另配）。FFN 直接讀 pool，無 host→Metal async copy、無 CPU FFN fallback。

6.1 建立流程（loader 端）

觸發: -ngl > 0 且 LLAMA_EXPERT_CACHE_ALLOW_NGL=1
       （沒有這個 env，-ngl>0 時 expert cache 整個不啟用 —— 顯式 override）

capacity = 2 * clamp(budget/(n_layers*per_slot), 8, 256)
  expert tensor 建在 Metal buft 上，ne[2] 縮到 capacity
  （LLAMA_EXPERT_CACHE_LAYER_CAPS 可讓單層例外，loader 與
   cache 兩側同讀一次 per process —— 兩側看到同一個容量）
載入後 adopt_pool_region: tensor 自身的 Metal storage
  收養為 pool region（非擁有）
prepopulate: 每層前 n_slots 個 expert 標 resident
  （table[e]=e，loader 預讀順序；last_use=0 = 滿時第一個被逐出；
   只到 usable_slots —— ZERO slot 啟用時保留最後一個）
  cold-start 量測: 122ms → 88ms

6.2 L4_SKIP_LAYER0（ blk.0 的特殊處理）

為什麼 layer 0 必須排除
blk.0 的專家 tensor 是全量 CPU skip-load tensor（不進 pool、沒有 adopted region）。若 hook 對它寫 slot id，mul_mat_id 會索引一個沒有 backing 的 pool slot → layer-0 垃圾污染整個網路。所以 LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0=1 讓 hook 對 il==0 寫恆等 remap（直接抄原始 expert id）並跳過 ensure_batch 與 union 記錄；prewarm_hot 同步跳過。L4 路徑必設，否則 pool 無 adopted region 直接炸。

6.3 L2 / L3A / L4 對照

層路徑FFN 讀取方式選項
L2gather（cache → 臨時 tensor）per-step memcpy預設（L3-B）
L3A靜態 per-layer slot pool（malloc）src0 指向 pool region，eval hook 只寫 remap（一次 int32 寫入）LLAMA_EXPERT_CACHE_POOL=1
L4Metal zero-copy同上 + pool 在 Metal + 無 CPU fallbackALLOW_NGL（L4 時 L3A 自動開）

§7 MTP 投機解碼全解

draft-mtp 模式：同一個 target model 的 nextn block 當 draft（解碼成本 ~1 層而非整個主幹），不需要獨立 draft model。這是 GGUF 裡帶 MTP head 的模型（如 Nail-Qwen3.6-MTP 載體）的原生投機解碼。

7.1 編譯隔離（MTP_SUPPORT）

Mac 兩段式（bit-identity 根基）: build_fork_llama.sh -DMTP_SUPPORT → 編進 libllama-common （staging API: release_context 等） build_prod_binary.sh: llama-simple 不帶 define → 0 個 MTP 符號 llama-speculative-simple 帶 define → MTP 路徑編入 Windows 例外: CMakeLists WIN32 區塊全域定義 （bcc22133f 的 MinGW 修復；MTP code 原本在 #ifdef 後從未編過） 所有 MTP 特有代碼包在 #ifdef MTP_SUPPORT 內

7.2 執行流程

init:  common_speculative_init_from_params
         對同一 model 建第二個 context（ctx_type=MTP、
         cparams.ctx_other=ctx_tgt 共享 KV）
         spec_init->release_context() 移交所有權（borrow+reset
         會 double-free，ASan 確認）
       ctx_tgt: llama_set_embeddings_nextn(true, /*masked*/false)
       ctx_dft: llama_set_embeddings_nextn(true, /*masked*/true)
         （masked 只對 batch.logits!=0 的 token 輸出）
       多 head: chain_heads，n_max clamp 到 n_mtp_layers

prefill: chunked（n_batch 切塊 decode ctx_tgt —— 讓每個 ubatch
         走 L4 pool 路徑），每塊後 process() 捕獲 hidden states

draft:  pending_h（上次 process 捕獲的最後一列 h_nextn）
         作為 batch.embd 餵 ctx_dft
         每步 llama_decode(ctx_dft) → top_k=10 greedy
         p < p_min 則停；chained heads 每步 seq_rm draft 區
         + llama_set_nextn_layer_offset(ctx_dft, i) 換 head

verify: [id_last, draft0..draftN-1] 一次 llama_decode(ctx_tgt)
         （共享 KV：MTP 不需 ctx_dft 重解 —— driver 的 process()
          已在 target decode 期間捕獲 verify hidden states）

accept: common_sampler_sample_and_accept_n
         從 target 分佈逐列取樣，接受與 sampler 一致的 draft 前綴
         至少回 1 token；部分接受且 use_ckpt_tgt 時 restore
         checkpoint、已接受 token 當下一輪 partial draft 重送
         全接受 → common_speculative_accept 提交

--spec-draft-n-max N → verify batch = N+1 tokens
  對應 CGC_POOL_MAX_TOKENS（預設 8 → 涵蓋 N≤7）

7.3 Staging API（src/llama-ext.h）

API用途
llama_set_embeddings_nextn(ctx, v, masked)控制輸出 nextn（pre-norm）embeddings；tgt 全 token / dft 只 logits 標記的
llama_get_embeddings_nextn(_ith)安全逐列讀取（_ith 有越界防護 —— MTP 修復點）
llama_set_embeddings_layer_inp(_ith)per-layer 輸入抽取（CGC_LAYER_BIN 載體，bit-bisect 用）
llama_set_nextn_layer_offset(ctx, off)選擇第幾個 NextN head（il = n_layer + off，多 head chaining）

7.4 verify / draft fast path（CGC_VERIFY_DECODE / CGC_DRAFT_DECODE）

觸發: verify_fast = CGC_VERIFY_DECODE && ctx=DEFAULT + embeddings_nextn + multi-token + seqmax>n_tokens-1 draft_fast = CGC_DRAFT_DECODE && ctx=MTP + 1-token （n_past==0 的極短 prefill 仍走精確路徑； MTP catch-up 與所有非 MTP 執行 → 精確 ensure_batch） 行為（跳過阻塞 ensure）: (1) zero_reserved_slot: 每層一次性把最後 slot 的 pool region 全 kind 清零（zero_slot_done 防重入） (2) touch: 只 bump resident 專家的 LRU + fast-path 遙測 （n_fast_cold = 真實穩態 decode miss 率 —— ensure 路徑 的計數不含 fast path，不量會誤判） (3) remap 用 slot_table_safe: resident → slot idx；cold → ZERO slot（slots_l-1） 品質代價 = 該步該專家零貢獻（影響 accept rate） 量測（steady MTP denseIQ4XS seed1）: cold ~65% 全階段穩定 → 結構性 churn（per-layer working set >> slots）， 不是 prewarm 能修的冷啟動集中 —— 有數據的取捨

不設這兩個 env時 verify/draft 走精確 ensure_batch = 位元組等同 base。要 bit-identical 驗收的 run 通常不開 fast path；生產要速度才開（並用遙測盯 cold 率）。

§10 已知陷阱與結論

10.1 無效／未接線旋鈕（誠實清單）

旋鈕現況證據
CGC_EVICTED_RING無效evicted_recent 只有 init resize 與讀取端（llama-context.cpp:1578），全 repo 無 push_back 寫入端 → ring 永遠空，re-prefetch 迴圈是死碼。設 0 或 16 行為相同（bit-identical 驗證組曾設 0）
CGC_GLU_FUSED_DOWN半接線device.cpp 只加大 pipeline smem；ops.cpp 的 fused dispatch 固定 ne02d=0（註解「0 disables fused-down」）→ .metal 的 fused-down 變體存在但 host 從未啟用
LLAMA_EXPERT_CACHE_TAILPIN / PREWARM_HOT / BATCH只剩註解runtime 無讀取（被 WIN_PIN、CGC_NO_PREWARM 反向開關、預設 worker pool 取代）

10.2 三條鐵律

繼承自血淚教訓
(1) BLAS / ACCELERATE / CPU_REPACK 永遠 OFF —— IQ3 系列亂碼是數值問題不是平台問題，三平台一體適用。
(2) bit-identical 的三支柱缺一不可 —— MM_BITIDENT（kernel M-invariance）、MTP_NO_WARMUP + NO_SEQ_RM_PROBE（cache 污染）、guard（無選項自動生效）。驗收失敗時按三平台白皮書 §8.2 排查表走。
(3) 所有 DBG/DUMP env 都是除錯用 —— 存在即生效、影響效能，生產 env 不該出現任何 *_DBG / *_DUMP / *_TRACE。

10.3 結論

本 fork 的價值主張可壓縮成一句：「動態載入的 MoE 推理，做到了 upstream 直接讀檔的位元組等同 + MTP 與非 MTP 的位元級一致，同時保留融合與管線化的效能」。五大訴求各有明確機制與選項（§1 表），90 個 env 的每一個都知道自己為什麼存在（§8），無效旋鈕誠實標註（§10.1）。三份白皮書構成完整文件鏈：本書講機制、CGC_MTP_Bit-Identical_技術白皮書 講修復過程與證據、CGC_三平台開發_技術白皮書 講落地與夥伴交付。
