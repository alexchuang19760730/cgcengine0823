§1 測試體系總覽：四層金字塔

本 fork 的測試不是單一大腳本，而是嵌在開發流程每一站的自動/半自動關卡。每一層失敗都擋住下一層 —— 從編譯到部署，任何一層的失敗都有明確的修復指引（§10）。

┌─────────────────────────────┐ │ L3 部署包驗收 │ 夾帶 dylib 自包含、 │ （拿到別台機器也能跑） │ bit-identical 重驗 ├─────────────────────────────┤ │ L2 Commit 後功能驗收 │ bit-identical 四方對比、 │ （品質證明） │ antiloop、MTP、效能 ├─────────────────────────────┤ │ L1 Pre-commit 自動測試 │ check_build_tracked.sh │ （每次 git commit 必跑） │ 5 項：dylib/symlink/exe/rpath ├─────────────────────────────┤ │ L0 Build 驗證 │ clean rebuild 100%、 │ （兩段式 + MTP 隔離） │ MTP 符號隔離、flag 紀律 └─────────────────────────────┘ 時間軸: 改代碼 → L0 rebuild → git add → L1 hook → commit → L2 驗收 → 打包 → L3 （L1 是自動的；L2/L3 是驗收跑，指令都收錄在 §9）
層名稱觸發時機自動化失敗後果
L0Build 驗證每次 rebuild半自動（2 個 script）不進 commit
L1Pre-commit每次 git commit全自動（git hook）commit 被擋下
L2功能驗收commit 後（重要變更、晉升 main 前）半自動（指令集 §9）不得晉升 main
L3部署包驗收更新部署包後半自動不得發佈

測試金字塔的設計原則：越下層越便宜、跑越勤；越上層越貴、只在里程碑跑。L1 的 5 項檢查 < 2 秒（純 git/otool 查詢），每次 commit 都跑；L2 的 bit-identical 四方對比每 run 要數分鐘（35B 模型），只在關鍵變更跑。歷史教訓：8/26 的 build 追蹤疏失（29.85 t/s build 一度救不回來）就是因為當時沒有 L1 —— 現在有。

§4 L2 功能驗收：bit-identical（核心品質證明）

fork 的硬性要求：投機（MTP）與非投機（llama-simple）在同 prompt/seed/greedy 下位元級一致。四方位對比矩陣是標準驗收法。

4.1 測試矩陣

FUSE=0 FUSE=1(+guard) simp A ──────────── B B == A（防護不該改數值） spec C ──────────── D D == C 跨路徑 C == A 的 16-token 前綴（spec 多 1-2 token overshoot） D == B 同前綴 通過 = 4 個 run 的續寫全部一致（byte-level）
ID測試通過標準最近結果
T-F1四方位輸出對比（simp F0/F1 + spec F0/F1）4 個輸出互相一致（simp 16-token = spec 前綴）8/30 PASS（修復前 B≠A：777/800 IDS 翻轉）
T-F2Expert-ID 一致性（CGC-IDS trace）同 (pmax, il) key 逐行比 → 0 差異（≤4000 行）8/30 PASS：simp 0/800、spec 0/422
T-F3Draft accept rate基準 prompt：12/12 = 100%8/30 PASS
T-F4guard 拒絕日誌（FUSE=1）CGC_MMV_FUSE_DBG=1 有 REJECT 記錄（有重疊時）且輸出不變8/30 PASS：simp 3 REJECT + 1 融合、spec 0 REJECT
T-F5bit-identical env 齊全性三支柱 env 都在：CGC_MM_BITIDENT + CGC_MTP_NO_WARMUP + CGC_NO_SEQ_RM_PROBE驗收指令內建（缺一即 T-F2 失敗）

row-wise 陷阱（bit-bisect 的教訓）：spec 的第一個 target eval 是 verify batch（M=3，pmax 涵蓋多位置）、simp 是 M=1 逐 token —— 直接拿相同 pmax 的 IDS 行相比是無意義的（不同 batch 組成）。正確做法是 row-wise（per-position）：verify batch 的 row0 對 simp 的對應 token。白皮書二的 ids 比較器已實作此邏輯。

§5 L2 功能驗收：antiloop 與穩定性

「沒 loop」= 不死鎖、不停滯。驗證 watchdog 體系在位且整個測試過程無 wedge。所有 L2 的長跑測試本身就兼任 antiloop 觀測。

ID測試方法通過標準最近結果
T-A1長跑無 stall任何 L2 測試（每 run 數分鐘、~2000 command buffers）跑 CGC_WATCHDOG=1無 CGC-WATCHDOG: stalled 日誌、rc=08/30 全 PASS
T-A2queue 鑑別能力在位watchdog 配置確認（不需真的觸發）CGC_WATCHDOG=1 且（需要時）CGC_DRAIN_EVERY 可開在位
T-A3無 race 提交順序確認 env 沒有 CGC_SUBMIT_AHEAD / CGC_TOPK_BOUNDARY兩個 bug 重現器都未設8/30 PASS
T-A4GPU OOM 暫態重試rc=138/SIGBUS 時 sleep 5 重跑一次重跑 rc=0（區分暫態壓力 vs 真失敗）8/30 驗證（部署包初測 138 → 重跑過）
T-A5prewarm / hook pipeline 無死鎖prefetch 關閉（MTP 安全模式 CGC_NO_PREFETCH=1）下整跑無 hang（歷史 deadlock 均為 bg-thread 與 verify 重疊）8/30 PASS
antiloop 的深層保證不是「測出來」的，是「設計出來」的
死鎖防線是結構性的：(1) 提交順序 race-free（hook 寫完 remap 才提交消費它的 buffer —— 預設行為，無選項）；(2) drain_layer 等同層 in-flight 填寫完成才繼續（防撕裂）；(3) pick_slot 寧可逐出也不等待（免死鎖）；(4) watchdog 60 秒硬止損。測試 T-A1–A5 驗證的是這些防線沒有被繞過。歷史 wedge 的完整翻案記錄在技術講解白皮書 §4.1。

CGC_LAYER_BINper-layer dump每層輸入對照（simp/spec 對稱 tag）chunk0 L4 rows0-2 發散 → 鎖定 warmup 污染假說

CGC_MM_DBG / CGC_MMV_FUSE_DBGkernel tracemul_mat kernel family / 融合決策確認 M-invariance 繞過與融合派送差異
A/B env 切換方法論單一變數開關對比（FUSE 0/1、warmup on/off…）v1–v10 的 bisect 骨架：一次只翻一個開關
row-wise 比較器方法論per-position 對比不同 batch 組成破解「pmax 相同但 batch 組成不同」的假分歧

方法論五律（從 bit-bisect 提煉，寫進所有測試）：(1) 一次只翻一個開關；(2) 比較前先確認兩邊 binary 相同（時間線上的 rebuild 會污染結論）；(3) batch 組成不同時先做 row-wise 對齊再比；(4) 用 pmax 歸屬 batch（非同步 stderr 順序不可信）；(5) 短 prompt 的分歧比長 prompt 乾淨（無「長 prompt 剛好贏 race」的僥倖）。

10.3 結論

本測試計劃的完整性承諾：每一個通過的 release commit，都能回答四個問題 —— (1) 從零 rebuild 可重現嗎（L0）？(2) binary 資產進版控了嗎（L1，8/26 教訓）？(3) MTP 與非 MTP 位元級一致嗎（L2 bit-identical）？(4) 拿到別台機器能跑且輸出相同嗎（L3）？—— 加上 antiloop 與效能數字，構成與四份白皮書（機制 / 修復 / 落地 / 測試）對應的驗收閉環。歷史武器庫（§8）保證失敗時不是從頭猜，而是按排查表走。
