2. 症狀：什麼是「0000 退化」

端點現場（8/30 晚，壞）復驗（8/31 乾淨環境，好）
/v1/chat/completionscontent = "0000..."reasoning = "The capital of France is **Paris**."
/completion（raw）content = "0000..."" the capital of the country of France. It is"
長生成（40 token）—（沒測到）正常思考文本，6.8 t/s（非 MTP 基線）
對照組 llama-simple（同 env）正常正常

0000 的本質：decode 輸出的 token ID 全部是 0。在 CGC 專家快取架構下，這是「專家權重讀到全零 → FFN 輸出歸零 → 模型退化到最平凡輸出」的典型病徵（與歷史上 slot table -1 → OOB 讀 → NaN 級聯同一家族）。

重點：simple 正常 + server 壞 = 當時直覺是「server 特有 bug」。這個直覺方向是對的排除法，但結論後來被推翻——見第 4 頁。

3. 排除法：六個假設逐一檢驗

#假設檢驗動作結果
1chat template 問題改打 raw /completion同症狀 → 排除
2kv_unified / 多 slot 併發--no-kv-unified -np 1同症狀 → 排除
3batch 太大繞過 pool-path-b 8 -ub 8同症狀 → 排除
4pool path 沒觸發log 遙測 CCG-PRE / CCG-POST有冷專家、有 slot 分配 → 排除
5本地代理污染回應curl -sv 看路由代理 7897 攔截 → 502 空回應，但無法偽造 JSON 內容 → 只解釋「空回應」，不解釋 0000
6記憶體壓力 / 殭屍行程重開機後單行程復驗三端點全健康 → 定案

方法論要點：排除法做到第 5 步時，「server 特有 bug」的假設空間已經很窄。但 panic log 的 panicked task = llama-server + jetsam 出現 484 次指向了另一個方向——記憶體。

4. 根因：記憶體超賣——一次根因，兩種表現

核心 panic 證據鏈（panic-full-2026-08-30-185924.0002.panic）：

  • watchdog timeout: no checkins from watchdogd in 91 seconds — 整機凍結 91 秒
  • panicked task = llama-server — 凍結時正在跑我們的運算
  • jetsam（記憶體殺手）出現 484 次 — 核心瘋狂搶救記憶體的痕跡
  • 任務表同時有 llama-server 與 llama-simple（兩個 13GB 級行程共存）

超賣的算術（16GB 統一記憶體）

記憶體大戶大小可逐出？
llama-server 模型載入（--no-mmap）13.2 GB進 page cache，壓力下可壓縮但難以及時逐出
llama-simple 對照（同視窗殘留）13 GB同上
CGC 4GiB Metal pool4 GBwired，核心完全不可逐出
macOS + IDE + 其他~4-6 GB部分 wired

→ 需求遠超 16GB → 壓縮/jetsam 追不上 → 核心執行緒餓死 → watchdogd 心跳斷 91 秒 → panic。

兩種表現：同一個記憶體超賣視窗，(a) 惡化到極端 = 核心 panic 重開機；(b) 中度 = 專家 pread 短讀/填充失敗 → blob 歸零 → 0000 輸出。加上 3 次 server 重啟風暴（每次重讀 13GB），就是我們看到的全部現象。

5. 調查途中的兩個插曲（值得單獨講）

插曲 A：本地代理的「假掛死」

Mac 上的 curl 預設走了本地代理（port 7897），代理攔截 127.0.0.1 請求回 502 空回應——症狀酷似 server 掛死。

Gotcha 入檔：本機 curl 測 localhost 必帶 curl --noproxy '*'。診斷順序：先 curl -sv --noproxy '*' 看清路由，再下「server 掛了」的結論。夥伴遠端連線不受影響（不走 Mac 的代理）。

插曲 B：一個錯誤結論的當場回收

調查中我曾建議「server 改 -c 1024 瘦身記憶體」。被追問後實算 KV 數學：

參數（從 GGUF 檔頭解析）值
head_count_kv（GQA）2（不是 16！）
key/value length256 / 256
KV per token2×2×(256+256)×2B×40層 = 4 KB
-c 1024 / 2048 / 4096KV 僅 4 / 8 / 16 MB

→ 相對 13.2GB 權重是 0.03% 雜訊，省它毫無意義還砍半上下文。結論收回，維持 -c 2048（與生產線一致）。

教訓：dense 模型的 KV 直覺不可移植到 GQA MoE——下記憶體結論前先算 KV 數學。

6. 修復與防護：run_server.sh（已落地）

根因是營運面（行程衛生），所以防護也是營運面——不是改 C++，是把紀律寫進啟動器：

防護內容
① 清殘留行程啟動前 pkill 舊 server / simple / speculative（殭屍是 0000 與 panic 的共同土壤）
② 記憶體水位檢查系統可用 <25% 直接拒跑並提示（13GB 模型 + 4GiB wired pool 的硬門檻）
③ 持久 log寫 Backup/cgc_logs/（重開機不滅證；/tmp 這次把診斷證據全吃掉了）
④ 健康輪詢 + 連線卡起來後自動驗 /health，印出 LAN IP、測試指令、--noproxy 提醒、停止方法
⑤ 參數對齊生產線-np 1 --no-kv-unified -c 2048 + 完整 CGC env + watchdog

夥伴用法：./scripts/run_server.sh → 等連線卡 → Windows 端直接指 http://<Mac LAN IP>:8080/v1（OpenAI 相容）。

7. 制度化教訓（給全團隊）

  1. 一次一個重工行程（鐵律） — server 運行期間，那台 Mac 禁止任何 13GB 級操作：llama-simple 對照、量化、HF 下載。行程疊加 = kernel panic，不是「慢一點」。
  2. 重啟前確認舊行程已死 — ps 確認，不是只按 Stop；短時間重啟風暴（每次重讀 13GB）本身就是記憶體轟炸。
  3. CGC_WATCHDOG 救不了 kernel 層 — 它是行程內 GPU watchdog；整機凍結要看 /Library/Logs/DiagnosticReports/panic-full-*.panic。判斷口訣：app crash 看 stderr，整機重開機看 panic log。
  4. 重要 log 即時寫持久路徑 — /tmp 會被重開機清掉，這次把現場證據全滅了。
  5. 先驗工具再看症狀 — curl -sv --noproxy '*' 十秒鐘分清「送不到」vs「模型輸出壞」。
  6. 下記憶體結論前先算 KV 數學 — GQA MoE 的 KV 是雜訊級，直覺會帶錯方向（插曲 B）。
  7. 「無法重現」本身是證據 — 當所有代碼假設排除且乾淨環境變好，根因在環境（記憶體/行程），要敢於定案不在代碼裡找。
