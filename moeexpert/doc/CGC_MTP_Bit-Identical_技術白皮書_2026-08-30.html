§1 摘要：決策與結果

硬性要求：投機解碼（MTP）與非投機（llama-simple）在相同 prompt、相同 seed、greedy sampling 下必須位元級一致（bit-identical）。本白皮書記錄完整的分歧 bisect 過程、兩個獨立根因（warmup 專家快取污染 + fused GLU kernel 的 galloc lifetime overlap）、修復方案（fuse 決策防護）與四方驗證結果。

指標修復前修復後（guard）
simp FUSE=1 vs FUSE=0（專家 ID）777/800 keys 分歧0/800 完全一致
spec FUSE=1 vs FUSE=0（專家 ID）0/422（本就無 overlap）0/422 維持一致
simp 16-token 輸出 vs spec 輸出分歧精確前綴（byte-level）
spec draft accept rate<100%12/12 = 100%
eval 速度（融合保留度）F1 127.77 ms/tokF1 127.77 vs F0 145.10 ms/tok（快 12%）
fused 派送（M=8 prefill chunk）多層融合（含危險層）安全層融合 il=1；危險層 il=3 拒絕 3 次

結論：兩條路徑、兩種 FUSE 設定（4 個組合）現全部位元級一致，且融合效能完全保留。分歧不是 kernel 數值本身，而是 galloc 記憶體規劃與 fused kernel 寫入時點的 lifetime 衝突 —— 是否觸發取決於計算圖形狀（節點數、MoE 前後排序），llama-simple 與 speculative MTP 的圖形形狀不同，導致「只有一邊壞」的詭異現象。

§2 現象與假說排除時間線

同一 prompt、seed=42、temp=0 下，spec 續寫與 simp 續寫從某個 token 開始分岔。Bisect 過程依序排除/確認了下列假說：

8根因 B 精確機制：galloc lifetime overlap拒絕記錄 CGC_MMV_FUSE_DBG：il=3 的 ffn_moe_weights-3 與 fused 輸出 ffn_moe_swiglu-3 記憶體重疊確認：讀到 garbage 的確定性污染
關鍵轉折
第 7 步是本 case 的轉折點：原本以為是「兩路徑的 fuse 決策不一致」，但 cross-FUSE 對比顯示 spec 是 FUSE 不變的（0/422），simp 卻不是（777/800）。若只是決策差異，兩邊都會變。單邊改變 + 圖形形狀相依 → 記憶體重疊假說。同一時間線上還發現 09:07 與 09:36 兩次運行的 binary 可能不同（09:40 有重建），先以 source mtime 釐清時間線後才下結論，避免拿不同 binary 的輸出互比。

§3 根因 B 機制：galloc lifetime overlap

fused kernel 把三個節點（mul_mat_id gate、mul_mat_id up、swiglu）壓成一個 dispatch，但 galloc 是按「未融合」的圖形規劃記憶體的。

═══ 未融合（galloc 的規劃依據）═══ node[gate]: dst = ff8_out_gate ──┐ node[up]: dst = ff8_out_up ──┤─ 之後 node[glu]: dst = ff8_out(c) ──┘ galloc 看到 glu 是最後寫入者 → c 的 range 可以和 「gate 之前就死掉」的張量重疊（lifetime 分析）。 ll=3 的 llama-simple 圖形中，gate 與 glu 之間還有 ffn_moe_weights-3 等中間張量被計算/讀取。 ═══ fused（CGC_MMV_FUSE=1 實際執行）═══ dispatch 發生在 GATE 節點位置： kernel 直接寫 c（swiglu 輸出）到「GATE 的時點」 ↑ 此時 ffn_moe_weights-3 還沒算完 / 還要被讀 ↑ 而 c 的 range 與它重疊 → ffn_moe_weights-3 讀到 garbage → argsort 近平手翻轉 → L4 專家順序翻轉 → 挑到不同 expert → 下游全分歧 ═══ 為什麼只有 simp 壞、spec 不壞 ═══ 是否重疊取決於圖形 SHAPE（節點數 / MoE 前後排序）： simp 圖（39 節點版本）：il=3 區間有重疊 → 壞 spec 圖（37 節點版本）：il=3 區間無重疊 → 好的 同一 kernel、同樣 fused，行為因路徑而異 → 偽裝成 「spec/simp 決策差異」或「kernel 數值差異」。

證據鏈：(a) CGC_MMV_FUSE_DBG 的 REJECT 記錄直接印出重疊張量名（ffn_moe_weights-3，k=5/6，介於 gate 與 glu 之間）；(b) TDCB in-compute dump 早先觀察到 ffn_shexp（共享專家）被污染 —— 與「gate/glu 區間的中間張量被覆寫」自洽；(c) spec 圖形無此重疊 → FUSE 不變；(d) 設 FUSE=0 後分歧消失。

§4 方案：fuse 決策的 lifetime-overlap guard

位置：ggml/src/ggml-metal/ggml-metal-ops.cpp（ggml_metal_op_mul_mat_id_glu_fused 的 fuse 決策處）。原則：防護性拒絕融合，而不是重寫 galloc —— galloc 的 lifetime 分析對未融合圖形是正確的，問題只在「融合改變了寫入時點」這個契約破壞。在決策點檢查即可，安全時仍融合（保效能），危險時走原路（保正確）。

// [CGC bit-identical 2026-08-30 v10] galloc lifetime-overlap guard.
// The fused kernel writes c (the swiglu output) at the GATE position, but galloc
// assigned c its memory based on the swiglu position: any range c shares with a
// tensor that is computed OR read strictly between the gate and the swiglu node
// makes the fused plan and the galloc plan disagree -> one of the two tensors
// reads garbage.
{
    static const bool guard_dbg = (getenv("CGC_MMV_FUSE_DBG") != nullptr);

    const char * c_base = (const char *) c->data;
    const size_t c_nbytes = ggml_nbytes(c);
    const ggml_backend_buffer_t c_buf = c->view_src ? c->view_src->buffer : c->buffer;

    auto range_overlap = [&](const ggml_tensor * t) -> bool {
        if (t == nullptr || t->data == nullptr || t == c) {
            return false;
        }
        const ggml_backend_buffer_t t_buf = t->view_src ? t->view_src->buffer : t->buffer;
        if (t_buf == nullptr || t_buf != c_buf) {
            return false;   // 不同 buffer 不可能重疊
        }
        const char * p = (const char *) t->data;
        const size_t nb = ggml_nbytes(t);
        return p < c_base + c_nbytes && c_base < p + nb;   // 區間相交
    };

    const int glu = *glu_idx;
    for (int k = idx + 2; k < glu; k++) {          // gate..glu 之間的每個節點
        ggml_tensor * t = ctx->node(k);
        bool hit = range_overlap(t);                 // dst 本身
        for (int s = 0; !hit && s < GGML_MAX_SRC && t->src[s]; s++) {
            hit = range_overlap(t->src[s]);          // 以及它的 src
        }
        if (hit) {
            if (guard_dbg) {
                GGML_LOG_WARN("[MMV_FUSE dbg] idx=%d/%d a=%s c=%s REJECT: galloc overlap with %s (k=%d) between gate and glu\n",
                        idx, ctx->n_nodes(), a->name, c->name, t->name, k);
            }
            return false;   // 拒絕融合 → 走未融合原路（bit-identical）
        }
    }
}

4.1 設計要點

設計理由
檢查 dst 與其 src 兩層「computed OR read」都要防：src 在區間內被讀也會踩到 c 已被提前寫入的 range
用 view_src 的 buffer 判同 bufferview 的 data 指向母張量，實體 buffer 才是判斷重疊的正確依據
只掃 idx+2 .. glu 區間gate 之前的張量 lifetime 已結束（galloc 保證），gate..glu 之間才是 fused 寫入時點提前的受害窗口
重疊即拒絕融合（fallback 原路）未融合路徑本來就 bit-identical；拒絕的代價只是該層失去融合加速，不是全域退步
CGC_MMV_FUSE_DBG 印 REJECT可觀測性：哪層、與哪個張量重疊、k 位置，直接對應 galloc 規劃

(1) 比較單位要對齊：verify batch（M=3）與 M=1 逐 token 的輸出必須 row-wise（per-position）比，直接逐行比會製造假分歧。(2) 二分「決策差異」vs「數值差異」的訣竅：同一條路徑內 toggle 開關（cross-FUSE），而不是只跨路徑比 —— 單邊不變、單邊改變即指向環境/記憶體相依。(3) 圖形形狀相依的 bug（galloc overlap）在「兩條圖形不同的路徑」對比下會自動現形。(4) 下結論前先確認 binary 一致性（source mtime / 重建時間線），避免拿不同 binary 的輸出互比。(5) 修這類契約破壞的最佳位置是「破壞方」的決策點（fuse 決策），而不是被依賴方（galloc）—— galloc 對未融合圖形是正確的。
