§3 Mac 兩段式 Build 設計（MTP 隔離，bit-identity 的根基）

這是本 fork 最重要的編譯設計：llama-simple（生產 non-MTP binary）與 llama-speculative-simple（MTP binary）從編譯期就隔離。MTP 的所有代碼變更都經 MTP_SUPPORT 編譯選項分離 —— 生產 binary 不含任何 MTP 代碼，這是「MTP 與非 MTP 位元級一致」硬性要求的建築基礎。

═══ 兩段式結構 ═══ Stage 1: scripts/build_fork_llama.sh cmake 全量編譯所有 dylib（Release + Metal） -DCMAKE_CXX_FLAGS="-DMTP_SUPPORT" │ │ 為什麼要 -DMTP_SUPPORT： │ MTP staging API（release_context 等，在 │ common/speculative.cpp）要編進 libllama-common │ —— 沒有它 MTP binary 無法 link ▼ build/bin/libllama-common.0.dylib （含 MTP staging API） build/bin/libggml*.dylib / libllama.0.dylib / ... Stage 2: scripts/build_prod_binary.sh 直接以 c++ 重編兩個 example、link 上述 dylib： llama-simple: 不帶 -DMTP_SUPPORT → binary 內 0 個 MTP 符號（生產 non-MTP） llama-speculative-simple: 帶 -DMTP_SUPPORT → draft-mtp 代碼路徑編入（MTP 模式） ═══ 隔離驗證方法 ═══ strings build/bin/llama-simple | grep -ci mtp → 0 strings build/bin/llama-speculative-simple | grep -i mtp → C 容器啟動 MTP 代碼路徑

3.1 Stage 1 關鍵 flag（一個都不能錯）

flag值原因
CMAKE_BUILD_TYPERelease生產效能
GGML_METALONApple GPU（M4 Max -ngl 99 全 offload）
GGML_BLASOFF（必須）BLAS（Accelerate）會造成 IQ3_XXS/IQ2_S 輸出亂碼
GGML_ACCELERATEOFF（必須）同上，正確性問題
GGML_CPU_REPACKOFF（必須）踩 IQ3 tensor 邊界
GGML_OPENMPOFF穩定性
LLAMA_BUILD_SERVER / APP / TESTSOFFapp/ 硬依賴 server-impl；SERVER=OFF 時一併關
GGML_MACHINE_SUPPORTS_sve/smeOFF預填結果，避免 configure 期檢查 binary 卡死（Apple Silicon 無 SVE/SME）
-DCMAKE_CXX_FLAGS-DMTP_SUPPORT把 MTP staging API 編進 libllama-common（僅 dylib 層；example 層的隔離在 Stage 2）

3.2 Stage 2 產物與 rpath

兩個 example 都以 -Wl,-rpath,"…/src/llama.cpp/build/bin" link 六個 dylib（libllama.0 / libggml.0 / libggml-cpu.0 / libggml-metal.0 / libllama-common.0 / libggml-base.0）。binary 位置固定在 src/llama.cpp/build/bin/（生產目錄慣例，且 dylib/exe 均被 git 追蹤 —— scripts/check_build_tracked.sh 會在每次 commit 時檢查）。

注意 Windows 夥伴：Windows 的 CMakeLists（if (WIN32) 區塊）目前是全域定義 MTP_SUPPORT（bcc22133f 設計，讓 MinGW binary 直接有 MTP 路徑）。這與 mac 的 per-binary 隔離不同 —— 兩條路都可用，但若要在 Windows 上完整複刻 bit-identity 架構，建議仿 mac Stage 2 的做法（llama-simple 單獨編、不帶 define），細節見 §5。

4.3 Bit-identical 驗收（新 binary vs 已驗證基準）

用與 bit-identical 白皮書同一組生產 env（seed=42、temp=0、n=16、FUSE=1 含 galloc guard），把重建後的 binary 輸出與先前已四方位元級驗證的基準比：

COMMON="CGC_EXPERT_CACHE_BYTES=4294967296 LLAMA_EXPERT_CACHE_ALLOW_NGL=1 \
LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0=1 LLAMA_EXPERT_CACHE_WORKERS=8 \
CGC_WAKE_POLL_US=15 CGC_PREFETCH_SRC=hist CGC_EVICTED_RING=0 \
CGC_OA_ASYNC=1 CGC_N_CB=8 CGC_GLU_FUSED_DOWN=1 \
LLAMA_EXPERT_CACHE_LAYER_CAPS=40-40:256 \
CGC_NO_PREFETCH=1 CGC_WATCHDOG=1 CGC_LAYER_BIN=1 CGC_MM_BITIDENT=1"

# non-MTP 生產 binary
env $COMMON CGC_MMV_FUSE=1 CGC_SIMP_TAIL_SPLIT=1 \
  build/bin/llama-simple -m $MODEL -ngl 99 --no-mmap -t 8 --seed 42 -n 16 -p "$P"
# → 輸出與基準 diff：IDENTICAL（bit-identical）

# MTP binary
env $COMMON CGC_MMV_FUSE=1 CGC_MTP_NO_WARMUP=1 CGC_NO_SEQ_RM_PROBE=1 \
  build/bin/llama-speculative-simple -m $MODEL -n 16 -ngl 99 -t 5 --no-mmap -s 42 \
  --spec-type draft-mtp --spec-draft-n-max 2 -c 3072 -expert-cache 4294967296 --temp 0 -p "$P"
# → 輸出 cmp 基準：BYTE-IDENTICAL；n_drafted=12, n_accept=12（100%）
驗收項結果
乾淨重建（rm -rf build → 全量）[100%] 無錯誤
兩段式隔離編譯llama-simple 0 個 MTP 符號；spec 有 MTP 路徑
simp（FUSE=1 + guard）vs 基準bit-identical
spec vs 基準byte-identical（cmp）
draft accept rate12/12 = 100%
fused GLU 派送il=1 融合生效（效能保留）

結論：mac release 路徑 完全可重現 —— 從零到 byte-identical 的驗收 binary，兩個 script 一口氣跑完。重建後的 binary 已連同本白皮書 commit 回 repo（binary 屬 git 追蹤慣例）。

6.2 驗收

與 §8 同一套（prompt/seed/env/binary 二元對比），只是兩個 binary 都是 CPU 路徑、無 Metal。bit-identical 的驗收不因平台改變 —— 這正是它的價值：同一份代碼在三平台應有一致的貪婪採樣行為。

鴻夥伴的交付清單
(1) 9d06e18ca 上 CPU-only build 完成（記錄編譯器版本與 flag）；(2) §8 驗收全項 + 輸出記錄；(3) t/s 效能數字（cache OFF 模式）；(4) 若 deploy-harmonyos/ 的 build.sh 與 §6.1 flag 有出入，以 §6.1 為準並回報差異。

§7 共享版組件（三平台的「遠端共享」層）

三平台不只是各自 build —— compute sharing 讓三平台的算力互通（端側 M4 / 雲側 / Windows 機器互為 prefill/decode 節點）。這層是 Python，無需編譯，三平台行為一致。

組件位置職責
DeviceProfileCGC-main/cgc_engine/pd/discovery.py節點能力畫像（OS/晶片/記憶體/後端）
EtcdServiceDiscovery / PDNodeRegistrar同上節點註冊與發現（etcd）
ComputeRouter（4D）CGC-main/cgc_engine/pd/router.pynetwork×hardware×model×runtime 四維矩陣選路由，含 prefill/decode 延遲估計
edge_server.py同目錄端側 HTTP 服務，--mtp 2 生產模式（內建 draft-mtp 參數、OOM 邊界 -mtp-ctx 3072、log 過濾防 token 流污染）
# mac 端起共享節點（實測指令）
python3 CGC-main/cgc_engine/pd/edge_server.py \
  --model models/gguf/Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf \
  --ngl 99 --no-mmap --mtp 2 --port 1234
# --mtp 2 內建：--spec-type draft-mtp --spec-draft-n-max 2 -c 3072

夥伴整合：Windows/鴻夢各自 build 出 binary 後，用同款 edge_server.py 包起來即成共享節點 —— DeviceProfile 會自動帶出平台畫像給 ComputeRouter 做跨平台路由。這是「三平台算力池」的接入方式。

§8 統一驗收標準（每個平台的 release 都要過）

驗收即「bit-identical 二元對比」：同 prompt、seed、貪婪採樣下，non-MTP 與 MTP 輸出必須位元級一致。這是本 fork 的硬性要求，平台無關。

8.1 驗收步驟

#步驟通過標準
1MTP 符號隔離檢查（§4.2）llama-simple = 0 個 MTP 符號；spec 有
2跑 non-MTP：llama-simple，§4.3 的 COMMON env + CGC_MMV_FUSE=1 CGC_SIMP_TAIL_SPLIT=1，seed 42、n 16rc=0、正常文本
3跑 MTP：speculative-simple，同 env + CGC_MTP_NO_WARMUP=1 CGC_NO_SEQ_RM_PROBE=1，--spec-draft-n-max 2 --temp 0rc=0
4輸出對比：simp 的 16-token 續寫是否為 spec 續寫的精確前綴（spec 會多 1–2 token 的 verify batch overshoot）前綴成立（byte-level）
5accept rate12/12 = 100%（此 prompt 基準）
6（加分）IDS 對比：兩 run 的 stderr 各取 CGC-IDS: 行，同 (pmax, il) key 逐行比0 差異

8.2 驗收失敗排查表

症狀最可能原因動作
spec 續寫從第一 token 就不同沒拿到 bit-identical 修復（b7364f886 之前）git log --oneline -3 確認基準含 9d06e18ca
無 MTP 二元缺 env（忘了 CGC_MTP_NO_WARMUP 等）驗收 env 沒帶齊嚴格用 §4.3 的 COMMON 完整集合

expert 選擇分歧（IDS 比對差異）fused kernel 在該平台的 galloc 行為差異先 CGC_MMV_FUSE=0 確認是否 kernel 融合相關；回報 binary + 平台 + flag 組合

Env 對照：完整生產 env 集合見 §4.3 的 COMMON。三個 bit-identical 關鍵 env（缺一不可）：CGC_MM_BITIDENT=1（M-invariant kernel 選擇）、CGC_MTP_NO_WARMUP=1 + CGC_NO_SEQ_RM_PROBE=1（專家快取污染修復）。galloc overlap guard 是純邏輯、永久生效，無 env。
