# CGC CPOT 分析工具白皮書 — decode 段深度分解（2026-08-29）

## 0. 摘要

本白皮書介紹 N30CACHE/CGC 生產棧的**時間分析工具鏈**，並用它完成一次深度的
steady MTP decode 段分解：把每個 decode step 拆成
**verify compute（Metal pipeline drain）/ catch-up fill（topk hook+pool 補填）/ graph submit（編碼提交）**
三個量測桶。核心結論（26.13 t/s clean run 實測）：

| 桶 | 實測（每 step） | 佔比解讀 |
|---|---|---|
| verify compute（wait） | 124.7 ms 等值 | **≥100% wall：GPU pipeline 完全飽和，CPU 全程跟隨** |
| catch-up fill（cb） | 1.5 ms | ~1.3%：補填**不是**瓶頸 |
| graph submit（submit） | 4.4 ms | ~3.9%：編碼很便宜 |
| 實測 step wall | 114.0 ms | GPU-bound 定案 |

污染態（session 連跑後 19.06 t/s）：wait 2326→3191 us/hook（**+37%**），
cb/submit 幾乎不動 → **page-cache 污染的退化全部落在 Metal pipeline（GPU 端）**，
不是 CPU 端、不是 I/O 執行緒端。通往 29.85 t/s 的唯一路徑 = 縮短 wait
（減 pool miss / 縮短 GPU 依賴鏈），而非再壓縮本來就 <2% 的 fill。

CPOT（cost per output token）= 1 / t/s：clean 38.3 ms/token、polluted 52.5 ms/token。

---

## 1. 為什麼需要這套工具

N30CACHE L4 池化 + MTP 投機解碼的 step 時間由三個異質成分構成：GPU 計算、
專家池補填、命令編碼提交。**不分解就無法歸因**：
- 速度掉了，是 GPU 慢了、補填多了、還是編碼開銷漲了？
- 記憶體污染（連續多輪 13GB 模型 + 4GiB pool）的代價落在哪一端？
- 「catch-up fill 是通往 29.85 的路」這個假說是否成立？

本工具鏈的回答方式：在 `ggml-backend.cpp` 的分段派發迴圈內建三個計時器
（CGC-SEG 遙測），再用 `decode_breakdown.py` 做窗口化差分與 per-step 換算。

## 3. 核心數據源：CGC-SEG 遙測原理

`ggml_backend_sched_graph_compute_async` 的 L4 池化分段派發
（[ggml-backend.cpp](file:///Users/alexchuang/Documents/flashkv0516/src/llama.cpp/ggml/src/ggml-backend.cpp#L1853-L1885)）：

```cpp
auto hook_seg = [&](int i) -> bool {
    // wait: 等第 i 段全部 n_cb+1 個 command buffer 完成（sched_yield 自旋）
    // cb:   callback_eval = topk hook（讀 topk id → 查 slot 表 → ensure 補填 → 寫 remap leaf）
    // submit: 下一段的 graph_compute_async 編碼+提交
    ...
    if (n % 160 == 0)
        fprintf(stderr, "CGC-SEG: wait %.1f cb %.1f submit %.1f us (%d)\n", ...);
};
```

三個語義要點：
1. **wait ≠ 純 GPU 計算**——它是「CPU 觀點的 Metal pipeline 排空時間」，
   含本段 GPU 執行 + 前面 submit-ahead 未排完的工作。submit-ahead 管線讓
   wait 可以跨 graph 累計，因此三桶**非嚴格互斥**（見 §5 解讀規則）。
2. **打印是累積平均**（`w_us/n`），視窗化差分才能還原「該窗口的真實平均」：
   `window_sum = avg_b × n_b − avg_a × n_a`，除以 `dn=160`。
3. **決定性（bit-identical）**：同 seed 同配置下 hook 總數、prefill/decode
   邊界完全一致（本配置：總 22240 hooks、prefill≈2400、decode 19840、
   370 steps、53.6 hooks/step ≈ 3 graph/step × ~17.9 段/graph），
   跨 run 只差牆鐘時間 → A/B 對比可信。

## 4. `decode_breakdown.py` 使用法

```bash
# 參數：err檔、prefill_hooks、steps、decode_wall_s、label
#   prefill_hooks = prefill 結束時的 hook 計數（≈2400，可用 watchdog stall print 對齊校驗）
#   steps         = decoded_tokens − n_accept   （MTP n_max=2 → 370）
#   decode_wall_s = err 檔內 "decoded N tokens in M seconds"
python3 scripts/diag/decode_breakdown.py /tmp/dlk2_P8.err 2400 370 57.833 "P8 polluted 19.06 t/s"
```

窗口選取：`n_b > prefill_hooks` 的窗口為 decode 期；`≤` 為 prefill 對照。
輸出 per-hook us、per-step ms（× hooks/step）、與實測 step wall 的殘差。

## 5. 深度分解實測（2026-08-29）

兩個同 seed steady run（carrier Nail-denseIQ4X，MTP n_max=2，8 workers，4GiB pool）：

```
===== P1 clean 26.13 t/s =====
total hooks=22240  prefill_hooks≈2400  decode_hooks=19840  steps=370
hooks/step = 53.6   decode wall = 42.18s
decode-phase per-hook us: wait=2326.2  cb=28.6  submit=81.3
per-step ms:  verify_compute=124.7  catch_up_fill=1.5  graph_submit=4.4
measured step wall = 114.0 ms
(prefill 對照 per-hook us: wait=3916.8 cb=147.5 submit=93.3)

===== P8 polluted 19.06 t/s =====
decode-phase per-hook us: wait=3191.3  cb=38.4  submit=131.9
per-step ms:  verify_compute=171.1  catch_up_fill=2.1  graph_submit=7.1
measured step wall = 156.3 ms
(prefill 對照 per-hook us: wait=4818.5 cb=140.1 submit=101.2)
```

### 解讀規則（重要）

wait 等值之和**超過**實測 wall ~9-15% 不是量測錯誤，而是管線並行的必然后果：
submit-ahead 讓 wait 涵蓋跨 graph 的 drain，且 CPU-split 的 CPU 子圖計算與
Metal wait 並行隱藏。因此正確讀法是：

- **wait ≥ wall ⇒ GPU pipeline 100% 飽和**：主執行緒整個 step 都在等 Metal，
  CPU 端（split 計算、sampler、KV）完全藏在 GPU 時間之下。**decode 是 GPU-bound。**
- 三桶佔比用**方向與相對變化**判讀，不做逐項相加閉合。

### 三個定案

1. **catch-up fill 只有 ~1.3-2%**（28.6→38.4 us/hook）。每 step 24 個 expert 的
   ensure_batch 補填成本 ≈ 1.5 ms——「把 fill 壓到零」最多拿回 ~2%，
   **不是**通往 29.85 的路（29.85 需 −26% step 時間）。
2. **submit 只有 ~4-5%**（81.3→131.9 us/hook）：9 個 command buffer/段的
   編碼提交很便宜，n_cb/編碼優化空間 <5%。
3. **污染退化 100% 落在 wait**：+865 us/hook（+37%），cb/submit 幾乎不動。
   page-cache 壓力是透過 pool miss 的 GPU 端 copy/同步變慢生效
   （13GB 模型擠壓 → pool 命中率下降 → 更多 miss fill 的 Metal copy），
   不是 CPU 或 I/O 執行緒。

### 通往 29.85 t/s 的路徑判讀

step wall 114→83 ms 需砍 31 ms，只能從 wait 裡拿：
- **減 pool miss**（實測 verify fast-path ZERO-mapped ~65% 結構性 churn）：
  routing-aware placement 或加大 budget（16GB 實體上限內空間有限）；
- **縮短 GPU 依賴鏈**：段間 submit-ahead 深度、n_cb 並行段平衡、
  GLU fused-down 類 kernel 融合擴大；
- **結構性**：n_max=2 已是實測最優（n_max=3 更差），accept 98.9% 無空間。

## 6. watchdog / probe（死鎖偵測與自救）工具

- `CGC_WATCHDOG=1`（run script 內建）：500ms tick，completion 停滯 >10s 觸發
  dump（9 個 buffer 狀態、expected/done 缺口、wedge_at 距 submit 毫秒數）。
- `CGC_WATCHDOG_CAPTURE=1`（= `N30CACHE_WATCHDOG_CAPTURE=1`）：stall 時加跑
  kernel 狀態捕捉（ioreg/memory_pressure/sample；每事件一次）。
- **探針提交本身即「踢」driver 恢復排程**（lost-wakeup kick）：
  P arm 2/2 stall run 自動復原（rc=0）。2026-08-29 repeat-kick 修復後，
  probe pair 改為**每次 dump cadence（15s）重複觸發 + recovery 後 re-arm**——
  D3/D13 證明一次性 probe 會讓第二事件無人踢而掛到 60s abort。
- `CGC_DRAIN_EVERY`（週期全 queue 排水）：**D arm 16 runs 已否決**——
  wedge 率 6/16（vs 無 drain 2/16，3×），2 次致命雙事件，速度零收益。
  原理：drain 製造「queue 排空 → 爆發重啟」= wedge 成形條件。維持 OFF。
- 判讀：same-queue ALIVE=tail 未堵（146ms=排在 wedge 後隨之排空）；
  fresh-queue ALIVE=device 健康（11-12ms）。

## 7. 已知工具陷阱

- `pread_usec` 是 16 worker 的**累計**值（≈2× 牆鐘）——禁止除以牆鐘當 I/O 佔比。
- 速度 A/B 必須重開機後做（連跑退化 26→19 t/s 是 page-cache 污染，非代碼回歸）。
- 尾段讀檔會誤判輸出退化——必須看全文（seed-1 尾段 degenerate 是 carrier 特性）。
- CGC-SEG 的 n 計數為 process 級 static：target 與 draft 兩個 context 的
  hooks 混在同一計數器（對分解無害，因窗口差分只用相對量）。
