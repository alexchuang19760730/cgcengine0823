§1 摘要：決策與結果

前一版（b23fb51 + event gate，CGC_EARLY 之前）的 event gating 淨成本約 5.8 t/s：gate 讓 submit-ahead 的 sched 在每層 poll/wait 序列化，即使 callback body 只剩 touch（~70µs）也拿不回速度。本白皮書決策：Early Write+Signal（CGC_EARLY） — 把 slot_table 寫入與 event signal 提前到 sched「等待 top-k segment 完成」之前，讓 write+signal 藏在仍在執行的 GPU segment 後面。

指標GATE（b23fb51 實測）CGC_EARLY（實測）NO_EVENT（上限，garbage）
Decode speed（255 token 同 prompt）17.75 t/s23.14–23.28 t/s23.47 t/s
與上限差距–5.7 t/s–0.33 t/s（1.5%）—
輸出品質✅ 正確✅ 正確（對齊 -ngl 30 base）❌ Garbage
hit rate（同 prompt）66.0%65.9%66.6%
prefetch（decode fast path）—2566 fills（bounded eviction 修復後）—

結論：CGC_EARLY 拿回 event gate 吃掉的大部分效能，與 NO_EVENT 上限只差 0.33 t/s（1.5%），同時保留正確輸出（NO_EVENT 之所以更快是因為直接丟掉同步 → race → garbage）。這是「要正確性、速度又逼近無 gate 上限」的甜點區。

§2 根因分析

兩個獨立問題疊加：(A) event gate 在 GPU critical path 吃掉 ~5.8 t/s；(B) prefetch_union 因 prepopulate 佔滿 slot 而形同 dead code，導致短冷啟動 prompt 的 routed cold experts 全落 ZERO slot、輸出退化。

2.1 Event gate 的淨成本

以 llama-simple 同 prompt、同長度（255 token 故事）做乾淨 A/B（t/s 不再被 EOG run-length 污染）：

設定callback bodygatet/s結論
NO_EVENT有（完整）無（race）25.32–23.47*上限，但 garbage
CGC_EARLY有（touch+union prefetch）有（提前 write+signal）23.14正確，逼近上限
GATE有（touch+union prefetch）有（post-poll write+signal）17.75正確，被 gate 拖慢

*NO_EVENT 的 25.32 是較短 run 的測量；255-token 同 prompt 下上限為 23.47。差別是固定開銷攤提，非真實速度差。

2.2 為什麼 gate 拖慢：wait 序列化 submit-ahead

═══ GATE（壞）：post-poll write + signal ═══ sched 迴圈（layer i）: poll seg[i]（等 GPU segment 完成 ──── 序列化點） │ GPU 空轉等 CPU callback 寫 slot_table callback: touch + prefetch + 寫 slot_table[i] + signal event(i) submit seg[i+1]（FFN 讀 slot_table[i]） → 每層的 write+signal 都在 GPU 完成「之後」，無法被 GPU 蓋住 ═══ CGC_EARLY（修）：pre-poll write + signal ═══ sched 迴圈（layer i）: callback_eval_pre: 寫 slot_table[i]（快 bump，不 build union/touch/pf） │ signal event(i) poll seg[i]（等 GPU segment 完成 ── write+signal 已提前藏好） │ GPU 這 810µs 期間 write+signal 已做完 callback (post-poll): touch + union prefetch（slot_table 寫入被抑制） submit seg[i+1] → write+signal 藏在執行中的 GPU segment 後面，gate 氣泡消失

2.3 為何「callback 只做 2.3µs」仍慢：gate 機制本身

對照實驗結果判讀
SPIN 100µs（callback 內空轉）19.59 → 11.07 t/s（砍半）callback 確實在 critical path
TESTNOOP（cbE=101µs）vs SKIPFAST（cbE=4.3µs）兩者 t/s 幾乎相同（~20.5）cbE 的 100µs 與 t/s 無關，另有其因

2.4 次要根因：prefetch_union 形同 dead code

L4 load 時 llama_expert_cache_prepopulate 把每層前 capacity–1 個 slot 標成 slot_owner=expert（表已「resident」）——所有 slot 都被佔住 → free-scan 找到 0 free slots → prefetch_union 永遠 queue 0。而 n_expert=256 > pool capacity=174，routed cold experts（≥174）在 decode fast path 無任何填補路徑，全被 map 到 ZERO slot。單 token prompt（無 prefill 可 prewarm）時 FFN 8 個 expert 中 3 個貢獻 0 → 輸出退化（"The The The"）。CGC_ROUTEDBG 實證：route=43->43 57->57 ... 181->-1 200->-1 238->-1。

§3 方案

3.1 Early Write+Signal（CGC_EARLY，ggml-backend.cpp + llama-context.cpp）

sched 端 — dispatch 迴圈在 topk_idx[i] 處、poll/wait 之前：

if (cgc_early && sched->callback_eval_pre && !cgc_no_event) {
    sched->callback_eval_pre(ttopk, false, sched->callback_eval_pre_user_data);
    signal_ev(split_backend, i);   // write + signal 提前
}
// ... poll seg[i]（等 GPU）...
if (!cgc_no_event && !cgc_early) { signal_ev(split_backend, i); } // GATE 才在此 signal

hook 端 — 新增 expert_cache_on_topk_pre：只寫 layer i 的 slot_table（快 bump，無 union build / touch / prefetch），讀 host 端 slot_table 把 cold → ZERO slot；主 hook 在 CGC_EARLY 下抑制 slot_table 寫入（只留 touch + union prefetch）。

正確性 — event gate 仍保證 write-before-read：seg[i] 的 FFN 以 waitForEvent(event(i)) 等到 slot_table 寫完才執行。只是寫入時機從「GPU 完成後」提前到「等待前」，被執行中的 GPU segment 蓋住。

3.2 prefetch_union bounded LRU eviction（llama-expert-cache.cpp）

  • 先數 routed cold members（table[e] < 0）——只 queue 當步 routed 的 cold experts，絕不 over-prefetch 預測。
  • free slots 不足時，逐出「最舊、非當步 union 成員、非 ZERO / pinned / queued / in-flight」的 slot，只補足 shortfall（bounded）。
  • 逐出同步釋放 slot_table[evicted] = -1，後續 pre-callback 寫入即把該 expert map 回 ZERO 直到重填。
  • 修復後 decode fast path prefetch 從 0 → 2566 fills，bg thread 在 decode 中積極 fill cold experts（fill_batch_usec=2.3s），速度不變。

3.3 為何早寫安全（與 GATE 的語意差異）

GATE 的 slot_table 反映「seg[i] 完成瞬間」的 residency；EARLY 反映「seg[i] 開始前」的 residency。差別只在 seg[i] 執行期間 bg fill 是否 landing——但該 fill 無論如何要等下一次 pre-callback 才會進 slot_table，因此 EARLY 只是把「這一步該用什麼表」的決定點稍微提前，並不會讀到半填的 slot（event gate 保證）。

§4 設計決策

決策點選擇理由
slot_table 寫入時機pre-poll（EARLY）藏在 GPU segment 後；GATE 的 post-poll 序列化 submit-ahead
pre 與 post callback 分工pre 只寫表；post 只 touch+prefetchpre 快 bump（~µs），無需 union build / lock 掃描
event gate 去留保留保證 write-before-read；NO_EVENT 雖快 0.33 t/s 但 garbage
prefetch 逐出策略bounded LRU（只補當步 cold shortfall）全量 LRU 逐出 = over-prefetch（先前 batch 版 18.93 t/s）；無逐出 = dead code（free=0）
cold expert 的 FFN 值ZERO slot（保留 slot，zero-init）bounded、self-correcting；比 garbage 好、比同步 pread 快
pool capacity < n_expert接受（174 < 256）低記憶體機型；cold experts 由 union prefetch 逐步填補

§7 風險評估

風險機率影響緩解
EARLY 表快照較早 → 冷 experts 多一步 ZERO（首 token 品質）低低pre-callback 只延後 1 步；union prefetch 補填；event gate 保證不讀半填
bounded eviction 逐出近期熱 expert低中（hit rate 微降）只逐出「非當步 union」最舊 slot；當步 routed 永不逐出
prefetch 增加 bg 讀取 → 記憶體/磁碟壓力中低只 queue 當步 cold members，量 bounded
run-to-run 輸出 nondeterminism（pool residency timing）中低輸出恆為合法（coherent / 與 base 同退化），非 garbage
llama-bench 無法跑 CGC path（load 後卡 Metal init）高中（量測）改用 llama-simple + 長非-EOG prompt 量穩態
