# 

MTP 要「轉正」的前提（見 `MTP轉正規劃書_v1.1.md`）是：

> **pool path（expert cache 走 32-slot pool）的 logits 必須與 base path（無 cache、走全量 expert 權重）bit-identical。**

只有 pool path 正確，MTP 的多 token 驗證才不會被錯誤的 draft/verify logits 帶偏（之前一直看到的 draft loop、accept rate 偏低、語義錯誤輸出，全部源頭在這裡）。

### 1.1 expert cache 的兩條路徑

| 路徑 | 觸發時機 | 行為 |
|---|---|---|
| **full path** | prefill / 大 batch（n_tokens > 1 或超過 pool 上限） | FFN 對「全部 expert 權重」做 mul_mat_id，routing 用原始 top-k expert id |
| **pool path** | decode 單 token（n_tokens == 1，且 union 塞得進 32-slot pool） | FFN 的 src0 指向 pool 記憶體區（zero-copy），**mul_mat_id 必須改用「slot index」而不是 expert id**，否則讀到錯的權重 |

pool path 與 base path 唯一的差異就是：**`ffn_moe_topk`（選出的 expert id）在下游 mul_mat_id 之前被「remap」成 slot index**。所有 bug 都集中在這個 remap 是怎麼產生的。

> 重要教訓：**A/B 的「Hello world」單一 case OUTPUT-IDENTICAL 不代表路徑正確**——同一套邏輯在 `-ngl 0` 的 60 個 case 全跑完後，仍發現 `il=15, step=1` 分歧。單一 case 驗證的可靠度不足。

## 3. 根因證據鏈（為什麼 remap 會壞）

經過 ROUTE2G / MMIDGRP / MMIDENT / CPUMMID / SRC0EXEC / OCPROBE 等一連串 debug hook，建立出完整證據鏈：

### 3.1 核心根因：hook 讀到「過期的」expert ids

`ffn_moe_topk` 這個 ids tensor **在 CPU 層之間被重複使用**（同一塊 buffer），而且 `graph_reserve` 階段就會**預先填入舊值**。因此：

- **hook 在 `ask=0` callback 讀 `t->data` 時**，對 multi-token batch，token ≥ 1 的 id 是**舊的 garbage**。
- 真正被 GPU/CPU mul_mat_id 消費的，是**當下 argsort 產生的新鮮 ids**。

### 3.2 證據：同一層、同一個 token，三處看到三組不同的 expert set

| 觀測點 | 看到的 expert set | 性質 |
|---|---|---|
| `ROUTE2G`（topk dispatch 當下） | `{14, 42, 30, 50, 8, 58, 1, 43}` | **stale**（buffer reuse 殘留） |
| `ROUTE2G_FULL`（對 logits 做 argsort） | `{8, 20, 29, 24, 39, 57, 63, 7}` | **真值** |
| `MMIDGRP`（mul_mat_id 分組當下） | `{8, 20, 29, 24, 39, 57, 63, 7}` | **fresh（= 真值）** |
| `MMIDENT`（mul_mat_id 進入點） | `{8, 20, 29, 24, 39, 57, 63, 7}` | **fresh（= 真值）** |
| `CPUMMID`（CPU 執行結束） | `{14, 42, 30, 50, 8, 58, 1, 43}` | **stale** |

→ hook 用 stale 的 `{14,42,...}` 去建 union、寫 remap leaf；union **漏掉真值 expert `39 / 63 / 7`**，這幾格的 pool slot 是 garbage → token-1 的 FFN 讀到錯權重 → logits 分歧。

### 3.3 為什麼 remap leaf 條件修正後 token-0 好了、token-1 還是壞

- 修正後：**remap leaf 只在 pool active / layer 在 pool 時建立**，避免非 pooled 層（CPU full-size 層、`L4_SKIP_LAYER0` 的 blk.0）對全尺寸 tensor 做 slot-index remap → 消除 OOB 讀取 / SIGSEGV / logits 崩潰。
- 驗證：**token 0 全層 bit-identical**（routing logits、expert id、remap、PDATA slot bytes 全一致）。
- 但 **token 1 仍分歧**：即使 routing logits / expert ids / remap / slot bytes 都一致，Metal `kernel_mul_mv_id` 對 small batch 的 token index 處理仍有差異；CPU 側 `CGC_CPU_MMID` 也發現 blk.1 up 層 base vs pool 分歧，疑似 src1 buffer aliasing 覆寫。

## 5. 開放問題與下一步建議

1. **先確認 -ngl 12 pool SIGSEGV 是「已知雷區」還是「新回歸」**
   - 需比對：這個 crash 是否由未提交的 `ggml-backend.cpp`（cmd buffer 計數）引起？把該 diff 暫時移除重建、重跑同一個 case。
   - 若是該 diff 引起 → 先釐清 submit-ahead 的完成判定，不要讓「等全部 cmd buffer」變成死等/提前斷言。
2. **回答「目前輸出到底對不對」**
   - 目前唯一可信的收斂工具是**完整 A/B**：多 prompt × 多 seed × 多 n × pmax，全 CPU 與 GPU 都要過，且要 dump raw logits 比對（不能只比生成文字——同一文字不保證 logits 相同）。
3. **決定 remap 的最終形態（這是核心分歧點）**
   - 目前「hook 寫 remap leaf」：單 token 可達 bit-identical，但本質上依賴 callback 時機，multi-token 讀到 stale ids，無法根治。
   - Path A「圖內 `ggml_get_rows`」：理論上消掉 race，但實測 garbage，**原因尚未釐清就 revert 了**——需要先搞清楚它 garbage 到底是 slot_table 資料錯、還是 get_rows 的 3D 索引語意用錯（`ggml_get_rows` 對 3D slot_table 的 index 語意從未被確認）。
4. **長遠**：remap 穩定後，才能回到 MTP 本身（draft prefill hook / accept rate / 品質），決定是否轉正。

> 一句話總結：**過去幾輪確實全在修 remap 的 bug，因為它是 pool path 與 base path 唯一的差異點；目前單 token 已收斂，但 multi-token（MTP 驗證）與 GPU 層還不穩，且 Path A 的失敗原因未解開之前，不該再盲目換機制。**

## 6. Review 結論（同日後續調查，2026-08-24）

### 6.1 驗證：-ngl 12 pool SIGSEGV **不是**未提交 ggml-backend.cpp diff 引起

- **靜態**：該 diff（`cgc_bufs` / cmd buffer 計數）整段在 `ggml_backend_sched_compute_splits` 的 `else if (getenv("CGC_OA_ASYNC") != nullptr && ...)` 分支內（L1735）。原始 crash 沒設 `CGC_OA_ASYNC` → 那段程式根本沒執行。
- **環境 A/B**：無 `CGC_OA_ASYNC` 與 `CGC_OA_ASYNC=1` **都是 RC=139**，crash 點完全相同（`CGC-CB: ffn_moe_topk-0 ask=0` 之後）。
- **Backtrace（lldb）**：crash 在 `libggml-cpu.dylib` 的 `ggml_compute_forward_mul_mat_id + 1020`（EXC_BAD_ACCESS，寫入 garbage address `0xd5b8a5d311eab0d8`）——**不是** libggml-base（diff 所在）。
- **確認實驗有效**：`strings` 證實 `ggml_metal_get_cgc_bufs` 已編進目前 18:50 的 libggml-base。

→ **結論：SIGSEGV 與那份 diff 無關**；它是「GPU 層 + cache + multi-token prefill 走 CPU `mul_mat_id` 的索引/形狀缺陷」這個已知 multi-token 問題的實例。`-ngl 0` 全 CPU 不崩（實測 IDENTICAL）。

### 6.2 確認：兩版都「沒有」get_rows，真正的差異是 cgc_done wait 計數

- 全 repo（含其他 llama.cpp 副本）都**沒有** `get_rows(slot_table)` / `ffn_moe_slot_table`。
- b23fb51（committed）與 working tree 的 graph builder 相同：都是 `set_output` remap leaf + CPU 寫 remap。
- 唯一差異在 `ggml-backend.cpp` 的 submit-ahead wait：
  - b23fb51（錯）：`target = done0 + i + 1` → 只等 i+1 個 completion，segment 0 第一個 cmd buffer 完成就 fire callback → topk node 未跑完 → **stale remap → garbage**。
  - working tree（對）：`target = done0 + (i+1)*bufs`（`bufs = n_cb + 1`）→ 等到整段完成，callback 讀到新鮮資料。
- **這個 fix 已經在 working tree（未提交）**，18:50 binary 已編入 → 「移植」動作已完成，只需 commit。

### 6.3 兩個 Blocker：光靠 cgc_bufs fix 到不了 25 t/s

| Blocker | 實測現象 | 位置 |
|---|---|---|
| **A. qwen36 L4 skip-load 載入失敗** | `tensor 'blk.0.ffn_down_exps.weight' has invalid data` → 模型載不進來（cache ON）。cache OFF 則 OOM（已知） | `llama-model-loader.cpp` 的 `create_tensor` L4 skip-load（production dylib `libllama.0.0.5` 有、目前 source 壞） |
| **B. multi-token prefill SIGSEGV** | `-ngl 12` + cache + 任何 multi-token prefill → CPU `mul_mat_id` garbage pointer write | `libggml-cpu` `ggml_compute_forward_mul_mat_id` 的 batch 索引處理 |

→ 25 t/s 是在 production dylib（`f00c86b` / `libllama.0.0.5`）上測的；目前 source-built binary 不是那顆。**先修 A（載入）→ 再修 B（prefill）→ 最後才 benchmark。**

### 6.4 方案內部矛盾提示

「callback 不寫 remap + GPU 用 get_rows 自己算」在兩版都**不可行**（沒有 get_rows 節點，callback 不寫 remap 則 `set_output` leaf 是空的）。正確形態 = 保留 callback 寫 remap，只把 wait 計數修對（即 cgc_bufs fix）。

## 7. Blocker A 修復（2026-08-24，同日晚間）

### 7.1 根因：L4 pool capacity 計算錯誤 → 8GiB budget 下 capacity(348) > n_expert(256) → tensor 被「放大」→ OOB read

- qwen36 UD-IQ3_XXS：**40 layers、256 experts、top-8**（metadata 確認）。production（`f00c86b`）**根本沒有** `compute_l4_pool_capacity`——它是 b23fb51 重建時新增的，公式 `cap = 2*clamp(budget/(n_layer*per_slot))` 是重建產物。
- 實測（修復前，目前 source build）：
  - **8GiB → `L4 metal pool capacity=348 slots/layer`**（348 > 256）→ `create_tensor` 把 `ne[2]` 設成 348 → tensor **變大** → `load_data_for` 讀 348 個 expert blob（檔案只有 256）→ **越界讀到後續 tensor 資料** → `ggml_validate_row_data` 抓到 NaN → `tensor 'blk.0.ffn_down_exps.weight' has invalid data`。
  - 4GiB → capacity=174（< 256，正常 shrink）→ **可載入、RC=0、hit 99%**。
- production 文件（§8.38 / 白皮書）qwen36 一致用 **4GiB → 200 slots/layer**（production formula 略異，但都 < 256）。**8GiB 對這個模型是錯的 budget**。

### 7.2 修復（[llama-model-loader.cpp create_tensor](file:///Users/alexchuang/Documents/flashkv0516/temp/llama_roadB/llama.cpp-master/src/llama-model-loader.cpp#L1394-L1402)）

```cpp
// CGC fix: never let the pool capacity GROW a tensor past its real expert count.
t_meta.ne[2] = std::min<int64_t>(t_meta.ne[2], (int64_t) expert_cache_pool_capacity);
```

任何 budget 下 shrink 永遠是真正 shrink（≤ n_expert），不可能再放大 tensor。

### 7.3 修復後實測（重建 libllama.0.0.25 + relink llama-simple）

| budget | capacity | 結果 |
|---|---|---|
| 8GiB | 348→**256**（clamp） | **載入成功**（不再 invalid data），但 runtime Metal OOM（`kIOGPUCommandBufferCallbackErrorOutOfMemory`）——full 256 experts 上 GPU = base 13.2GB > 11.45GB 場景，**意料之中**；8GiB 對本模型不可用 |
| **4GiB** | 174 | **RC=0、載入 + 跑 + hit 99%**（production 文件一致） |
