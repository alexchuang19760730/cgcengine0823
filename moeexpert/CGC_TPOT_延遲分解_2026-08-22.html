結論：30 t/s（33.3ms）低於 IQ3_XXS 的純 kernel 地板（35ms/28.6 t/s）。也就是說——用目前的 Qwen3.6-35B-A3B-UD-IQ3_XXS 模型 + 現有 kernel，任何軟體層優化（hook 隱藏、kernel fusion）最多到 ~28.6 t/s，到不了 30 t/s。GPU 45ms 牆本身（weight-read bandwidth-bound + dispatch bubble）已佔 22.2 t/s 上限。

⑤ Proposal：是否有辦法達到 30 t/s（除 MTP）

分三層評估：軟體優化 / kernel 重寫 / 模型側。30 t/s 需要 step 從 64.6ms 壓到 33.3ms（-31ms）。

Path A：消除 hook 序列化（fix submit-ahead race）→ ~20.8 t/s
把 14ms 的 hook 序列化藏進 GPU 執行（ahead 重疊）。但 submit-ahead 的 remap race 是硬問題：GPU 可能在 hook 寫完 remap 前就讀取 → 錯誤輸出。event-gate（GPU 等 hook blit）會把 idle 加回去 → 無淨收益。需 GPU-side data dependency（slot table 查表，08-19 的「GPU remap」方向），複雜度高、收益 ~21 t/s（未到 30）。
Path B：kernel fusion（重建 08-19 的 fused MoE FFN + 更多 fusion）→ ~25-26 t/s
08-19 的 CGC_FUSED_MOE_FFN（fused gate+up+GLU+down 單 dispatch）在目前 build 不存在。重建它可把 GPU 牆 45 → ~38ms（fused 少 dispatch bubble）。配 Path A → ~26.3 t/s。中等工程（kernel fusion，數天-數週）。仍 < 30。
Path C：kernel 重寫（IQ3 inline dequant + sequential access）→ 28.6 t/s（地板）
08-19 估 3-6 週大工程。達到純 kernel 地板 35ms = 28.6 t/s。仍是天花板，不是 30。
Path D（唯一能超過 30 的無 MTP 路徑）：縮小模型側 / 降低 active bytes → 33-36 t/s
GPU 牆 = weight-read（bandwidth-bound）。把 IQ3_XXS 換成更小的量化（IQ2_XS / IQ2_XXS，weight 再砍 ~25-35%）→ weight-read 24.9 → ~18ms → GPU 牆 ~28-30ms → 33-36 t/s。
代價：IQ2 在 35B 的輸出品質風險（35B@IQ2 ≈ 20B@IQ4 的品質位階），且需重新做模型轉換 + 重驗 bit-identity。這是「換模型」而非「換引擎」，與 MTP 一樣是模型側手段。
Verdict：30 t/s 在目前模型 + 現有 kernel + 本硬體上，無 MTP 不可達。
理由：30 t/s = 33.3ms，低於 IQ3_XXS 純 kernel 地板（35ms/28.6 t/s）。軟體優化（A/B/C）最多到 28.6 t/s。唯一 30+ 的無 MTP 路徑是 Path D（更小量化 IQ2），屬模型側變更，非純引擎優化。

務實建議：若 30 t/s 是硬需求，優先序 = (1) MTP（排除在外）→ (2) Path D IQ2 模型（最快達 30+，但品質風險）→ (3) Path B kernel fusion（穩健到 ~26 t/s）。若品質優先，接受 15.5-17 t/s（正確路徑）或投資 Path B 到 ~26 t/s。
