§1 摘要：決策與預期

b23fb51 的 ngl 99 + expert-cache 產生 garbage（"!!!..."）。本白皮書決策：路線 B — 恢復 pin-CPU topk 鏈，讓 routing 與 hook 在 CPU split 上以有效數據執行，Metal 只算 FFN。結構上消除 remap race，同時移除 segmented dispatch 的 submit-ahead 開銷。

輸出品質❌ Garbage（"!!!..."）✅ Correct（bit-identical to base）
Decode speed21.48 t/s（production 配置實測）~23–25 t/s（詳見 §6）
Hit rate62.4%（routing 已污染）~95–99%（routing 正確後）
Dispatch 結構segmented per-topk + sched callback 讀 GPU argsortscheduler per-layer split + hook 在 CPU split
Callback 角色remap 寫者（raced）remap 寫者（CPU 端，無 race）

決策依據：b23fb51 把 pre-b23fb51 的「pin-CPU ffn_moe_probs」機制（run_n30cache.sh 引用的 llama-context.cpp:3489，§8.77/8.78）移除，改成「segmented Metal dispatch + sched callback 讀 GPU argsort」——這一改同時造成 garbage（remap race）與速度下滑。路線 B 是恢復並修正原始 production 設計，而非從零新寫。

§2 根因分析（修正版）

2026-08-25 以 production 配置（run_n30cache.sh，-n 64）實測 b23fb51：garbage 輸出、hit rate 62.4%、eval 2723ms/62 runs = 43.9ms/token = 21.48 t/s、CGC-SEG wait 906µs / cb 3.0µs / submit 91.8µs、RSS 8.82GB。

2.1 b23fb51 相對 production 的架構變化（關鍵）

pre-b23fb51（production，25–27 t/s）b23fb51（實測 21.5 t/s + garbage）
routing 計算位置CPU split（ffn_moe_probs pin CPU）Metal split（gate matmul + argsort 上 GPU）

2.2 三個壞點

壞點機制證據
A. Remap race（decode 主因） segmented dispatch 的 callback 在 seg(i+1) 已 submit 後才寫 remap_i，Metal 可能已用舊 remap 跑完 FFN_i（ggml-backend.cpp 迴圈：先 submit 後 callback，無同步） callback 3.0µs vs submit 91.8µs——callback 太晚
B. cgc_done 提前滿足 → 讀未完成 argsort cgc_done 只掛 main command buffer（ggml-metal-context.m），target=done0+i+1 可能在 segment 非同步尾 buffer 未完成時就滿足 SEGDBG vs CBD 對同一 topk 讀值不同；prefill il=2+ identity
C. Prefill 不載入 pool callback 在 n_tokens>1 只 record_routes；且 prefill 也走 segmented dispatch，il=2+ 讀到 stale argsort prefill il=2+ 路由 identity（[8j..8j+7]）
白皮書 v1（08-24）修正紀錄

R1 — 根因模型錯一半：v1 說 garbage 從 first decode（pool 空）開始；但實測 prefill il=2+ 已 identity，且 sequential（每段 synchronize）路徑也復現 → 不是「pool 空」單一原因，是 segmented dispatch 的時序/讀取問題。

R2 — "gate 被 repoint" 假設錯誤：v1 把 NaN 歸因於 gate_inp aliasing。實測 routing gate（gate_inp）不在 cache_ffn_tensors、不會被 repoint（llama-context.cpp 只 capture ffn_moe_gate/up/down/gate_up）。真正壞點是 callback 時序，不是 gate repoint。

M2 — 刪除 clamp 建議：v1 的 §4.3「clamp expert ID」會選到錯誤 expert；正確 fallback（union>slots 走 L3-B gather）已存在。

M3 — Phase 1 過度設計：v1 的 per-layer two-phase 手動分段是繞路；路線 B 由 scheduler 的 backend 指派自然產生相同的 per-layer 交錯結構。

§3 方案：路線 B — pin-CPU topk 鏈

核心原則：任何消費 remap/pool 的 split，執行前 remap 與 pool 已就緒。把 routing 鏈 pin 到 CPU split，hook 在 CPU 端以有效數據寫 remap；scheduler 的 split 順序保證 Metal FFN split 在 remap 寫入後才執行。不需要手動分段、不需要 event gate、不需要禁 fused-down。

3.1 架構對照

═══ b23fb51（壞）：segmented Metal dispatch ═══ Metal: seg[i] = [.. FFN(i-1) .. gate_i .. argsort_i .. topk_i] └─ callback 讀 GPU argsort ─→ 寫 remap_i（太晚，seg(i+1) 已 submit） Metal: seg[i+1] = [FFN_i(讀 remap_i，可能是舊值) .. gate_{i+1} .. topk_{i+1}] → race → garbage ═══ 路線 B（修）：pin-CPU routing + scheduler per-layer split ═══ Metal split: [layer_i attn → hidden_i] (async) │ Metal→CPU copy hidden_i（~16KB，unified memory） ▼ CPU split : [gate_i → probs_i → argsort_i → topk_i → weights_i] │ hook 在 CPU split 完成時觸發（數據有效）： │ read topk ids → ensure pool → write remap_i ▼ Metal split: [FFN_i = mul_mat_id(pool, hidden_i, remap_i) → 加權 → 輸出_i] │ ▼（下一層重複） scheduler 保證：CPU split 完成（remap 已寫）→ Metal FFN split 才執行 → 無 race，remap 永遠新鮮

3.2 為什麼結構上無 race

ggml_backend_sched 依圖拓撲順序執行 splits：gate_i→topk_i（CPU）在 FFN_i（Metal）之前；CPU backend compute 為同步，callback 在 split 完成後立刻觸發、寫 remap，之後才 submit Metal FFN split。FFN 的 mul_mat_id 讀 remap_ids leaf 時，remap 已被 CPU hook 寫好。submit-ahead 的 race 窗口被 scheduler 的順序性消除。

3.3 實作要點

要點 1 — pin routing 鏈到 CPU（llama-context.cpp graph_get_cb）

  • 對 ffn_moe_probs（softmax 輸出）呼叫 ggml_backend_sched_set_tensor_backend(sched, cur, cpu_backend)，反向傳播讓 gate matmul + argsort + topk 一起留在 CPU split。
  • 回歸 b23fb51 之前的 pin 機制（run_n30cache.sh §8.77/8.78），但只 pin routing 鏈，不 pin FFN。

要點 2 — hook 觸發粒度

  • CPU routing split 的最後節點可能是 ffn_moe_weights（非 topk）。hook 需改為：偵測 routing 鏈任一節點（topk/weights/probs）即觸發，並從該 split 的 topk ids 讀取（或由 callback 傳入 split 內 topk tensor）。

要點 3 — dispatch 改回純 async（移除 segmented per-topk）

  • 回歸 CGC_OA_ASYNC 的「Metal split 整體 async、無 per-layer callback」路徑（ggml-backend.cpp 保留無 topk 時的 async 分支即為此）。刪除 segmented 迴圈 / cgc_done 輪詢 / submit-ahead。

要點 4 — prefill 也載入 pool

  • 移除 n_tokens>1 的 early return；prefill 結束時 pool 已 warm（§4.3），第一個 decode step 不空轉。

要點 5 — 保留既有修正

  • il=0（L4_SKIP_LAYER0，無 pool region）remap 寫 identity（e→e），不 ensure/gather。
  • fused-down 保持啟用（GLU gate 屬 FFN，repoint 到 pool 是正確的；routing gate 不受影響）。

3.4 關鍵成本：Metal→CPU hidden copy

routing gate 需要每層 attention 後的 hidden state。decode（1 token）時為 [n_embd=4096] = 16KB/層 × 40 層 = 640KB/step，unified memory 下每個 copy ~µs 級，非同步執行可與 GPU 尾段重疊。CPU gate matmul（4096×256）~10–30µs/層，同樣可被 GPU 前層 FFN 覆蓋。這是路線 B 的主要新增 CPU 負擔，量級遠小於 GPU 層時間（~900µs）。

§4 設計決策（修正版）

4.1 Routing 來源

方案結論說明
CPU gate matmul（v1 提案）❌ 不可行IQ3_XXS 反量化太慢（~50ms/層）
讀 GPU argsort（b23fb51）❌ racesegmented callback 時序問題；且 il=2+ 已污染
CPU argsort from CPU probs（路線 B）✅ 採用probs 在 CPU split 同步算出，argsort 讀取無 race；~10µs/層

4.2 GPU argsort 去留

v1 的「buffer aliasing、已實測不可靠」說法不成立——實測差異是 async race（提前讀），非靜態 aliasing。路線 B 下 argsort 在 CPU 算，GPU 端 ffn_moe_argsort/topk 節點隨 routing 鏈一併移到 CPU，不需 graph surgery（scheduler 依 backend 自動切分），自然解決。

4.3 Prefill pool loading

移除 n_tokens>1 的 early return：prefill callback 也 ensure_batch + drain，pool 在 prefill 結束時已載入 routing 決定的 experts。prefill 只跑一次，不影響 decode throughput。

4.4 Pool capacity vs n_experts

不採用 clamp（會選到錯誤 expert）。既有 fallback 已正確：uni.size() <= slots 走 pool 路徑，否則走 L3-B gather 路徑。routing 修正後 hit rate 應回到 ~95–99%，union 超限機率低。

4.5 Fused-down 相容性

保持啟用（CGC_GLU_FUSED_DOWN=1，+6.5%）。v1 的「gate 不能 repoint」混淆了兩個 gate：routing gate（gate_inp，不 repoint，probs 有效）與 GLU silu gate（fused gate_up 的一部分，repoint 到 pool 是 FFN 的本意）。路線 B 下兩者天然分離，不需禁 fused-down。

4.6 同步手段

完全交給 scheduler 的 split 順序 + CPU 同步 compute。不需要 event gate、cgc_done 輪詢、手動 submit-ahead。這也消除了 b23fb51 的 done0+i+1 脆弱的 cgc_done 算術。

§5 實作計畫

Phase 1：Correct（優先）

Step 1 — Diagnostic（前置驗證，~30 min）

  • production 配置下 dump prefill 的 layer 2 gate logits（NaN? ramp?）與 layer 1 FFN 輸出，確認 il=2+ 污染的實際來源。
  • 確認 gate_inp 的 data pointer 未被 repoint（R2 驗證）。

Step 2 — pin-CPU routing（llama-context.cpp graph_get_cb）

  • pin ffn_moe_probs 到 CPU backend（~15 行）。
  • hook 觸發改為「routing 鏈任一節點」並正確取得 topk ids（~20 行）。

Step 3 — dispatch 回歸純 async（ggml-backend.cpp）

  • 移除 segmented 迴圈 / cgc_done / submit-ahead，走既有「無 topk」async 分支（~30 行刪減）。

Step 4 — prefill pool loading（llama-context.cpp hook）

  • 移除 n_tokens>1 的 early return，prefill 也 ensure_batch（~10 行）。

Step 5 — 驗證

  • ngl 99 + cache：輸出 bit-identical 對齊 base（-ngl 30 或 ngl 99 no-cache 若可跑）。
  • 速度：production 配置測量，目標 ~23–25 t/s。

Phase 2：Tuning（可選）

  • Metal→CPU hidden copy 非同步化 / 與 GPU 尾段重疊。
  • CPU gate 多執行緒（-t 8）或 reuse 已計算的 probs（避免重複 softmax）。
  • hit rate 回歸驗證（預期 95–99%）。

6.3 預測

誠實估

樂觀：CPU gate/copy 完全與 GPU 重疊、submit 開銷消失 → ~25 t/s（回到 production 水平）。

中性：CPU gate 每層 ~30µs 部分曝露 → ~23 t/s。

保守：hidden copy 或 split 順序有額外同步 → ~22 t/s（與現在持平，但輸出正確）。

v1 白皮書的「-4%→24.5 t/s」與「+5.5ms(+14%)」算術有誤（39.2+5.5=44.7ms 應為 22.4 t/s）；本版以實測 43.9ms 為基線重算。
