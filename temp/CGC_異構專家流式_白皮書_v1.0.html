核心洞察：llama.cpp 靜態圖把「完整 3D 專家張量」（ffn_gate_up_exps / ffn_down_exps，末維 = 全部 128 個專家）傳進 build_moe_ffn，但 ggml_mul_mat_id 每次只訪問 top-k（8 個）選中的專家列。
因此「讓權重留在磁碟、按路由流式載入」可以 100% 復用原計算語義 —— 需要的不是改 kernel，而是 改權重的存取來源。
部分承擔計算硬體內存佔用為什麼
A 部分（llama.cpp）attention · router(ggml_argsort_top_k) · lm_headCPU常駐（小，~1-2GB）dense 計算量小、層間依賴強、不易並行
B 部分（expert-streamer）FFN 的 ggml_mul_mat_id（gate/up/down）GPU（或 CGC_WEIGHTS buffer）僅槽位容量（slots×expert_size）MoE 權重佔全模型 80%+，但單步只訪 top-k → 流式化收益最大

兩階段執行模型

decode 先算路由（selected_experts）→ 再按 top-k 載入專家 → 權重訪問。prefill 保持 mmap 路徑以降複雜度。

目標：20 tok/s

在不分頁（resident ≤ 16GB 槽位容量）的前提下，以 B→A 階梯逐步逼近（不依賴 MTP）。

先 B 後 A 階梯

P1 = Option B（per-step gather，純 CPU 側、零 kernel 動、可獨立 A/B）；P2 = Option A（計算期攔截換指針，B 之上的 kernel 精修）。

三、Expert Streamer 核心（C API）

cgc_engine/cpp/expert_streaming · cgc_expert_streamer.h / .c · 快取、預取、PD、緊湊模式

Slot Buffer 快取

每層 streamer 持 slots 個固定槽；cgc_expert_streamer_load_experts 做 miss-only 讀入 + LRU/phase 換出。telemetry 累計 requests/hits/misses → 真實命中率。

純 LRU 為主（3GB 預算實證）

sim（r3_trace）實測：pin 90/layer → hit 掉到 44.6%，純 LRU 82.9% → 3GB 下純 LRU 為主；Hot Pool 靜態 pin 僅在預算寬鬆或 profile 證明有效時小規模（top-8/16）啟用。

層迴圈預取（L4 手法）

真實路由已知後 → 對該步實際用到的層集合做下一層早讀（8 執行緒並行、非阻塞 PrefetchVirtualMemory）。不做跨 token 的 predict_next（證偽，見 §13.15/13.16）。同步 pool_prefetch_load 會阻塞關鍵路徑（實測 5× 變慢）。

PD 分離

prefill / decode 層分配到不同 GPU（CGC_EX_PREFILL_GPU / CGC_EX_DECODE_GPU），負載均衡 + 並行預取。

緊湊 slot 連續區域模式

region_bases[r] + slot*region_stride[r] 連續排布，讓 ggml_mul_mat_id 用 src0->data = region_bases[r] + ids 重映射即可直讀（Option A 前置條件）。

slot refcount / 生命週期

每個 slot 帶 refcount（pinned / 使用中 / 可逐出）。GPU 或計算未完成前禁止 free——完成後由完成-callback 遞減、refcount==0 才可逐出。第一大崩潰來源（GPU 未完成前 free slot → corruption/OOM）在此制度化。

數據源選擇：ReadFile 直讀磁碟（定案）

常駐內存 嚴格等於槽位容量（slots × expert_size），才能真正「流式替代整模型常駐」。mmap demand-paging 的省記憶體只是表象（TLB / page-cache 假象）——embed 每步只 gather 4KB、物理佔用 ≈2MB（參見 Qwen36 線 §13.104 教訓）。

四、llama.cpp 集成點

build_moe_ffn 路由 hook + Option B gather（P1）→ Option A 計算期攔截（P2）+ cgc_plan 分區

4.1 圖構建期：build_moe_ffn 路由 hook

llama-graph.cpp:1476-1491：
selected_experts = ggml_argsort_top_k(ctx0, selection_probs, n_expert_used) → 對 ggml_cont 獨立副本設 OUTPUT（保護 buffer 不被後續層覆蓋）→ res->register_moe_route(il, route_copy)。
之後 build_lora_mm_id（ggml_mul_mat_id）以 selected_experts 訪問 gate_up / up / down 三組權重。
注意：selected_experts 同時被 4 個 mul_mat_id + 4 個 add_id + 5 個 get_rows 共用——任何「重映射 ids」都不能在共享張量上原地改，這是 Option B 比 Option A 更安全的原因（B 不碰 ids）。

4.2 P1 · Option B：per-step gather（純 CPU 側、零 kernel 動、主路線）

不改 ggml_mul_mat_id kernel、不改 ids：在 build_moe_ffn 內，路由已知後，用 ggml_get_rows（gather）把 top-k 選中的權重列從 ffn_*_exps 抽成緊湊 per-step 張量（[k, n_ff, n_used]），再喂給標準 ggml_mul_mat_id。
階梯意義：L2 cache → per-step gather → 標準 mul_mat_id；selected_experts 保持全局 id 不動 → add_id / get_rows 全兼容。可獨立 A/B（gather 開銷 vs 省下的整張量 mmap 觸碰），P1 起點。

4.3 P2 · Option A：計算期攔截（ggml-cgc partition 循環，kernel 精修）

ggml-cgc.cpp:1342 cgc_backend_graph_compute：對每個 partition 做 ggml_graph_view → ggml_backend_graph_compute(inner)。
攔截點：在內層計算前，掃描含 MUL_MAT_ID 的子圖 → 讀 ids → 查 streamer（build_region_ids）→ 把 src0->data 換成 region_bases[r] + 重映射 ids。
v1.1 修正：這是 B 之上的 kernel 精修（省掉 per-step gather 拷貝），須先有 B 的正確性與命中率作為基線；且 ids 重映射需為共享張量做副本（見 4.1 注意），由完成-callback + refcount 保證 slot 存活。

4.4 cgc_plan 分區：路由與 mul_mat_id 切分

新增 expert-stream 分區，把 argsort_top_k（路由）與 mul_mat_id（計算）切到不同 partition，使「先算路由、後建 FFN 圖」的兩階段在 CGC 後端層面成立。

✅ P1 · Option B：per-step gather（主路線）

  • 純 CPU 側改動、零 kernel 動、零 ids 改動
  • gather 後接標準 mul_mat_id，add_id/get_rows 全兼容
  • 可獨立 A/B 量化開銷，正確性階梯的最低階

⏭ P2 · Option A：計算期攔截（kernel 精修）

  • 換 src0 指針 + ids 重映射，省去 per-step gather 拷貝
  • 需處理共享 ids 張量（副本）+ refcount 存活保證
  • 以 B 的命中率/正確性為基線再做 A/B

預測式預取（證偽）

「算 N 預取 N+1」的 predict_next（保留 top_k-1+高頻）即 miss-prefetch——預測對長尾撐不起 speculative read（§13.15/13.16），實測淨負。改採真實路由已知後的下一層早讀。

層迴圈預取（真實路由已知）

token t 的 30 層路由全部已知後 → 對 t+1 實際用到（且未入槽）的層集合做 8 執行緒並行早讀 + 非阻塞 PrefetchVirtualMemory；命中率 = 純 LRU 82.9%（r3_trace）。

命中率量測

load_experts 同時累計 total_requests/hits/misses → 純 LRU 82.9%（3GB 預算）vs 靜態 pin 90/layer 44.6%。

#10/#11/#12 已定案：#10 真實路由喂 streamer（修復 _drain_routes 引用清空 bug：items = list(_route_buf); _route_buf.clear()）；#11 雙緩衝命中率 37-44% 是 predict_next 的結果（證偽，非真實路由已知的層迴圈）；#12 當前淨負（memory paging + streamer cache 未集成），下一步以 Option B（gather）深集成 slot buffer 取代 mmap。
