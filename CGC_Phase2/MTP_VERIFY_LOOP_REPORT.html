1. 实现概览

完成了端侧 MTP (Multi-Token Prediction) verify loop 的完整实现，包含三种 draft 引擎、 正确性验证、端到端 benchmark 和 Hermes Router 集成。核心目标是将 MTP head 的 4 层 transformer 编译为 ggml computation graph，在 Metal GPU 上原生执行，消除 Python per-op dispatch 开销。

2. 三种 Draft 引擎对比

引擎 实现方式 ms/step 正确性 方差
ggml Native ctypes → libllama.dylib → Metal GPU graph 6.5ms 10/10 vs PyTorch ±0.79ms
MLX Metal PyTorch checkpoint → MLX arrays → Metal 7.4ms 20/20 vs ggml ±9.5ms (高方差)
PyTorch CPU torch.no_grad() forward on CPU 9.5ms — (reference) ±3.1ms
ggml Native 优势:
  • 最快: 6.5ms/step (比 MLX 快 1.14x, 比 PyTorch CPU 快 1.46x)
  • 方差极低: ±0.79ms (MLX 为 ±9.5ms, 受 Python GIL 影响)
  • 完全在 C/Metal 层执行, 无 Python per-op dispatch (11 ops × ~1ms = ~11ms 节省)
  • 单次 ggml_backend_graph_compute 调用执行整个 24-op 计算图

4. 关键发现: MTP 交叉点分析

核心问题: Qwen2.5-0.5B 太快, MTP 无法获益

Baseline 83.4 tok/s 远超 MTP 交叉点 (~42 tok/s)。 即使实现完美 zero-copy (2ms/step) 和 100% accept rate, 最高可达 TPS ≈ 74, 仍低于 baseline。

MTP 收益数学模型

每轮 (num_draft=4):
  - verify 时间 = (1 + accept_len) × base_decode_ms
  - draft 时间 = 4 × draft_ms_per_step
  - 有效 TPS = (1 + accept_len) / (verify + draft) × 1000

base_decode_ms = 1000/83.4 = 12.0ms (Qwen2.5-0.5B on M4)

情景分析 (base = 83.4 tok/s):
  100% accept, 0ms draft:  5 / (5×12) = 83.3 tok/s (勉强持平)
  100% accept, 2ms draft:  5 / (60+8) = 73.5 tok/s (0.88x, 仍有害)
  100% accept, 6.5ms draft: 5 / (60+26) = 58.1 tok/s (0.70x)
  25% accept, 6.5ms draft: 2 / (24+26) = 40.0 tok/s (0.48x, 实测一致)

结论: base > 42 tok/s 时, MTP 有害 (draft+verify 开销 > 节省的 decode)

5. Accept Rate 差异分析

指标 v1 checkpoint v2 checkpoint
训练数据量 7K samples 23K samples
离线 chain_acc 82% 76%
离线 nd=1 accept 81% 91%
离线 nd=4 accept 49.2% 56.6%
端到端 accept 19.4% 25.0%
差异原因:
  • 离线 chain_acc 在训练数据上测量 (同分布), 端到端在真实生成上测量 (分布偏移)
  • v2 (23K samples, 10 epochs) 可能过拟合, 离线 nd=1=91% 但端到端仅 25%
  • 代码 prompt 的 token 分布与训练数据 (ShareGPT + code) 有差异
  • MTP head 的 attention 简化为 seq_len=1 (无 KV cache), 可能限制长程预测能力

7. ggml Native 实现细节

架构

PyTorch checkpoint (.pt)
    ↓ torch.load → numpy float32
ggml weight tensors (ggml_new_tensor_2d/1d)
    ↓ ggml_backend_alloc_ctx_tensors → Metal GPU
ggml computation graph (24 ops):
    concat_in → mul_mat(proj) → rms_norm → mul(norm1)
    → mul_mat(V) → mul_mat(O) → add(residual)
    → rms_norm → mul(norm2)
    → mul_mat(gate) → silu → mul(up) → mul_mat(down) → add(residual)
    → rms_norm → mul(norm_out) → mul_mat(lm_head) → logits
    ↓
ggml_backend_graph_compute (单次 Metal GPU 调用)
    ↓
logits → Python argmax → draft token
mtp_hidden → 下一轮 chain 输入

关键技术决策

  • 预拼接输入: 用 np.concatenate([hidden, embed]) 替代 ggml_concat, 避免维度不匹配导致的 ggml_can_mul_mat 断言失败
  • Python argmax: Metal backend 不支持 ARGMAX op, 改为 ggml_backend_tensor_get 读回 logits 后在 Python 中 np.argmax
  • no_alloc=True: weight context 使用 no_alloc=True, 通过 ggml_backend_alloc_ctx_tensors 分配 GPU 内存
  • 本地 embedding copy: 保留 _embed_local numpy 数组用于快速 token embedding lookup (~0.01ms), 避免每次从 GPU 读回

8. 下一步方向

A. 测试更慢的目标模型 (最高优先级)

MTP 框架已验证正确, 只是需要 base < 42 tok/s 的模型才能获益。 可选: Qwen2.5-1.5B/3B (需下载 GGUF + 训练对应 MTP head), 或 Qwen3-VL-2B (已有 GGUF, 但 hidden_size=2048 需新 MTP head)。

B. 改进 MTP head 训练质量

当前 accept rate 仅 19-25%, 远低于离线 chain_acc 82%。 可尝试: 更多训练数据 (50K+ samples), 更短训练 (避免过拟合), 学习率调度, 或使用真实代码 prompt 数据收集。

C. True zero-copy 优化

当前仍有 ggml_backend_tensor_set/get 的 CPU↔GPU 拷贝 (~0.1ms on unified memory)。 理论上可通过共享 Metal buffer 消除, 但需深入 ggml 内部 API。 实际收益有限: draft 从 6.5ms → ~2ms, 但 baseline 83.4 tok/s 时仍无法超过。

D. 增大 num_draft

当前 num_draft=4, 若增大到 8 或 16, 可摊薄 draft 开销。 但需要更高的 accept rate 才有收益, 且 llama.cpp verify 逐 token 进行。

9. 结论

端侧 MTP verify loop 的三种引擎 (ggml Native / MLX / PyTorch CPU) 均已实现并验证正确。 ggml Native 是最快的引擎 (6.5ms/step, 100% token match), 通过 ctypes 直接调用 ggml C API 在 Metal GPU 上执行完整计算图, 消除了 Python per-op dispatch 开销。

然而, Qwen2.5-0.5B on M4 太快 (83.4 tok/s), MTP 无法带来加速。 MTP 交叉点约为 42 tok/s, 当前模型远超此阈值。 端侧 MTP 的正确应用场景是较大的模型 (如 3B+), 或云端慢模型 (如 Gemma4 26B: 26 tok/s base)。
