2.6 当前 PD 决策逻辑（ComputeRouter 4D 矩阵）

已实做在 CGC-main/cgc_engine/pd/router.py。 路由决策不基于 token 长度，而是基于 4D 能力矩阵：(D1) 网络质量、(D2) 硬件算力、(D3) 模型参数、(D4) 运行时状态。

D2 算力评分公式

# router.py → _device_compute_score()  → 0-100 分
ram_score  = min(total_ram_gb / 64.0, 1.0) * 25    # RAM 占 25%
gpu_score  = min(gpu_vram_gb / 24.0, 1.0) * 25    # GPU VRAM 占 25%
cpu_score  = min(cpu_cores / 16.0, 1.0) * 20       # CPU 占 20%
net_score  = max(0, (200 - network_latency_ms)) / 200 * 15  # 网络占 15%
load_score = (1 - current_load / 100.0) * 15        # 负载占 15%
# → 总分 0-100

# Mac M4 16GB:  min(16/64,1)*25 + min(11.2/24,1)*25 + min(10/16,1)*20 + 15 + 15 = 59.0
# Windows 8GB: min(8/64,1)*25  + min(2/24,1)*25    + min(4/16,1)*20  + 15 + 15 = 27.5

能否跑模型的判断

2.7 FusionRoute 在 Prefill 阶段的实做细节

核心洞察： FusionRoute+MoT 的价值在 Prefill 阶段最大。Prefill 时每个 token 都要过 attention → 选错专家代价大（O(n²) 重算）。FusionRoute 在这里做 token-level 路由，让每个 token 都被最强专家处理。Decode 阶段每次只生成 1 个 token，选错代价小，可以只用一个专家。

2.7.1 谁跑 FusionRoute？

机器RAM跑 FusionRoute？原因

2.7.2 Prefill 阶段：FusionRoute 做什么

Mac M4 Prefill 机器上的完整流程：

1. 收到 prompt: "debug this crash in expert_cache.cpp"

2. Tokenize → [token_0, token_1, ..., token_N]

3. 对每个 token，FusionRoute Router 做决策：

   token_0 "debug" → weight_proj(hidden_state) → [0.3, 0.7]
                                                   Qwen  Ornith
                                                   ↑     ↑
                                                   低分  高分 → 选 Expert B (Ornith)

   token_1 "this"  → weight_proj(hidden_state) → [0.8, 0.2]
                                                   高分  低分 → 选 Expert A (Qwen3.6)

   token_2 "crash" → weight_proj(hidden_state) → [0.2, 0.8]
                                                   低分  高分 → 选 Expert B (Ornith)

   ... 每个 token 独立打分，分数变化自然产生切换 ...

4. 当专家切换时，KV Translation 介入：

   token 0-49: Expert A 处理 → KV cache A [50, 2, seq, 256]
   token 50:   切换到 Expert B!
              → KV Translation: W_ridge × KV_A → KV_B (O(n) 线性映射)
              → latency: ~278ms (32K context) → 目标 < 1ms (MoT)
   token 50-80: Expert B 处理 → KV cache B [30, 2, seq, 256]
   token 81:   切回 Expert A
              → KV Translation: W_ridge × KV_B → KV_A
   token 81+:  Expert A 处理

5. Prefill 完成 → 发送 hidden_state [seq, dim] 给 decode 机器

2.7.3 Router 决策：每 token 独立打分

# src/fusion_route/router.py 核心
class Qwen3Router(nn.Module):
    def __init__(self, hidden_size=2048, n_experts=2):
        self.weight_proj = nn.Linear(hidden_size, n_experts)  # 2048 → 2
    
    def forward(self, hidden_states):
        # hidden_states: [batch, seq, 2048]
        scores = self.weight_proj(hidden_states)  # [batch, seq, 2]
        scores = F.softmax(scores, dim=-1)        # 归一化
        return scores  # 每个 token 的专家分数

# scores[0] = Expert A (Qwen3.6) 的适配度
# scores[1] = Expert B (Ornith-1.5) 的适配度
# 没有"切换触发器"——每个 token 独立打分，分数变化就导致切换

2.7.4 KV Translation：O(n) 线性映射

# src/kv_translation/ridge_mapper.py 核心
class RidgeKVMapper:
    def __init__(self, n_layers=40, n_heads=2, head_dim=256):
        # 映射矩阵: 逐层逐头
        # W_ridge shape: [40, 2, 256, 256]
        self.W = nn.Parameter(torch.zeros(n_layers, n_heads, head_dim, head_dim))
    
    def translate(self, kv_source, layer, head):
        # kv_source: [seq_len, 256] (源模型的 KV cache)
        # O(n) 线性映射，不是 O(n²) attention 重算
        return kv_source @ self.W[layer, head].T  # [seq_len, 256]

# KV 兼容性验证 (Qwen3.6 vs Ornith-1.5):
#   num_key_value_heads: 2 = 2 ✅
#   head_dim: 256 = 256 ✅
#   num_hidden_layers: 40 = 40 ✅
#   → 可以直接做线性映射，不需要 head 对齐或投影

2.7.5 Complementary Logit：双层修正

# src/fusion_route/complementary.py 核心
class ComplementaryLogit(nn.Module):
    def __init__(self, hidden_size=2048, vocab_size=152064):
        self.correction = nn.Linear(hidden_size, vocab_size)  # 修正网络
    
    def forward(self, z_expert, hidden_state, alpha=0.1):
        # z_expert: 专家输出的 logits
        # hidden_state: 当前层的隐藏状态
        # alpha: 修正强度 (0=不修正, 1=全修正)
        c = self.correction(hidden_state)           # 计算修正量
        z_fuse = z_expert + alpha * c               # 叠加修正
        return z_fuse

# 内层修正: KV Translation 修正 KV cache (数值层面)
# 外层修正: Complementary Logit 修正 logits (输出层面)
# 双层叠加 → 品质提升 5-15%

  • Mac: FusionRoute + KV Translation → Prefill
  • Windows: 只跑 Qwen3.6 decode
  • 品质来源: Prefill 用 FusionRoute 选最强专家
  • 速度来源: Windows decode 用 MTP 加速

场景 2: Mac prefill → Mac decode

双机协作

  • Mac A: FusionRoute + KV Translation → Prefill
  • Mac B: FusionRoute + KV Translation → Decode
  • 品质最高: 两端都跑 FusionRoute
  • 每个 token 都选最强专家

场景 3: 纯端（单机）

离线

  • Mac: FusionRoute + KV Translation + Prefill + Decode
  • 全部在一台机器完成
  • 速度最快: 无网络延迟
  • Expert Cache 命中率最高

2.7.7 Prefill vs Decode 的 FusionRoute 价值对比

阶段FusionRoute 价值KV TranslationMTPComplementary Logit
Prefill ✅ 最大 — 每个 token 过 attention，选错代价 O(n²) ✅ 用 — 切换专家时翻译 KV 可选 ✅ 用 — 修正 prefill logits
Decode ❌ 低 — 每次只生成 1 token，选错代价 O(1) ❌ 不用 — 只有一个专家，不需要切换 ✅ 用 — 加速 decode 2-3x ✅ 用 — 修正输出 token
一句话总结： FusionRoute+MoT 的核心价值在 Prefill 侧——用 token-level 路由让每个 token 都被最强专家处理，然后把高质量的 hidden_state 传给 Decode 机器做快速生成。这就是"P" 的含义：Prefill 决定品质，Decode 决定速度。
