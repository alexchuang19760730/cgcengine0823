# 檢討報告：8/26 原版 Build 遺失事故（29.85 t/s 無 cap）

- 事故日期：2026-08-26 ~ 2026-08-27
- 事後補救完成：2026-08-27
- 嚴重度：**高** — 關鍵生產 build（29.85 t/s 無 cap）一度無法完整從 git 還原，只能靠「沒 commit 的檔案 + 湊合的舊 dylib」勉強運行，並衍生 batch cap、garbled output、GPU OOM 等連環故障。

---

## 1. 事件摘要

8/26 22:22–22:23 在 nested 生產 repo
`temp/llama_routeB/llama-src/temp/llama_roadB/llama.cpp-master/build/bin` 產出了 **29.85 t/s 無 cap** 的關鍵 build：

- `libllama.0.0.15.dylib` / `libllama-common.0.0.15.dylib` / `libmtmd.0.0.15.dylib`（無 n_batch cap 版本）
- `libggml*.0.19.0.dylib`
- `llama-simple` / `llama-speculative-simple` / `llama-bench`

這套產物在 git 中有**兩個洞**：

1. **有追蹤但漏 commit**：build/bin 的 10 個檔（symlink + exe）已被 git 追蹤，但改動一直沒 commit。只要有人 `git checkout`，這些未 commit 的「原版」就會被覆寫。
2. **完全沒追蹤**：`0.0.15` 系列版本化 dylib 被 `.gitignore` 的 `/build*` 一刀切**靜默忽略**，`git status` 完全不顯示，等於零防護。rebuild 一覆寫就永久遺失。

再加上 nested repo 長時間處在 **detached HEAD**、rpath/symlink 被改動沒有記錄、兩處 build 目錄互相混淆，最終導致：

- production 載入不相容 dylib → `prompt exceeds batch size`（cap 到 17）
- 與 dense-iq4x 模型不相容 → MTP accept rate 0%、garbled output
- 還原過程又踩 GPU Metal working set 上限 → `kIOGPUCommandBufferCallbackErrorOutOfMemory`

## 3. 疏失清單（全部 root cause）

### 疏失 A：漏 commit（有追蹤、未入庫）
- **事實**：build/bin 的 10 個檔（`libggml*`、symlink、exe）有被 git 追蹤，但從 8/26 22:22 起一直沒 commit。
- **後果**：`git checkout` 時被舊版覆寫，「8/26 原版」的準確內容無法從 git 完整重建，只能靠記憶 + 殘骸拼湊。
- **根因**：沒有「build 完成 → 立即 commit」的紀律；當時 session 停在「做完、未提交」狀態就結束。

### 疏失 B：沒追蹤（關鍵產物被 `.gitignore` 靜默忽略）
- **事實**：`.gitignore` 的 `/build*` 把整個 build 目錄一刀切忽略。版本化 dylib（`0.0.15`/`0.0.17`）放在被忽略目錄內，git **完全看不到**，`git status` 顯示乾淨、`git add` 會被靜默跳過。
- **後果**：rebuild 覆寫後 `0.0.15` 永久遺失（本次靠 `.bak` 殘骸 + 記憶才救回），只能退而求其次用 8/20 的 `0.0.5`。
- **根因**：ignore 規則沒有替「必須追蹤的 build 產物」開例外；也沒有人定期 `git status --ignored` 檢查「該追蹤卻被忽略」的檔案。

### 疏失 C：在 detached HEAD 上工作
- **事實**：nested repo 長時間 `HEAD detached from f810fa5`，reflog 顯示在 4 個 commit 間反覆 `checkout`。
- **後果**：任何一次 checkout 都可能讓未 commit 改動/孤立 commit 消失；而且「以為在 branch 上」的錯覺讓人不 commit。
- **根因**：沒有確認 `git status -sb` 的 branch 狀態就開始動工。

### 疏失 D：rpath / symlink 被改動無記錄
- **事實**：nested `llama-speculative-simple` 的 `@rpath` 被改到 ROOT build/bin；`libllama.0.dylib` symlink 被指到 `0.0.17`（含 cap）或與模型不相容的版本。改動沒有 commit、沒有 changelog。
- **後果**：production 載入錯誤 dylib → batch cap / garbled output，且「為什麼壞」無法從 git 追溯。
- **根因**：`install_name_tool`/`ln -s` 是「改檔案」不是「改 code」，容易被當成不用 commit 的操作。

### 疏失 E：兩處 build 目錄互相覆寫、混淆
- **事實**：存在 ROOT `temp/llama_roadB` 與 nested `temp/llama_routeB/llama-src/temp/llama_roadB` 兩套 build，且 nested 的 exe 會動態載入 dylib。rebuild 靜默覆寫 working binary，無版本化保存。
- **後果**：不知道 production 到底吃哪一套；working build 被覆寫後無法回滾。
- **根因**：沒有把「golden build」複製/封存到安全位置，也沒有在 script 裡固定 BIN 路徑的驗證。

### 疏失 F：無 golden artifact 回歸防護
- **事實**：29.85 t/s 只有「當下跑過」的紀錄，沒有：dylib 哈希、exe/dylib 集合的對照表、自動驗證 script。
- **後果**：壞掉時無法快速比對「現在的 build 是不是 29.85 那套」。
- **根因**：效能紀錄（session memory）與 artifact 本身分離，沒綁在一起。

### 疏失 G：環境記憶體壓力被低估（非 code，但加劇事故）
- **事實**：本機 M4 16GB unified，Metal `recommendedMaxWorkingSetSize = 11453 MB`（11.45GB）。35B ngl99 全 offload + expert cache + MTP draft ctx 超過上限；且 IDE/Doubao 等 GPU 消耗者共享 working set，另曾出現 swap 100% 滿 + 12.8GB 壓縮記憶體。
- **後果**：還原後的驗證 run 直接 OOM（`kIOGPUCommandBufferCallbackErrorOutOfMemory`），無法原地重測 29.85 t/s。
- **根因**：16GB 機器跑 35B 全 offload 本來就在臨界點，需要乾淨 GPU 環境（關 GPU-heavy app / 重開機）才能重測。

## 4. 已採取的補救措施（2026-08-27）

### 還原 8/26 原版
- nested exe `@rpath` → **nested roadB `build/bin`**（otool 驗證）。
- symlink：`libllama.0.dylib → libllama.0.0.15.dylib`（8/26 22:23 無 cap）、`libllama-common.0.dylib → libllama-common.0.0.15.dylib`、`libggml.0.dylib → libggml.0.19.0.dylib`。
- ROOT：`libllama.0.dylib → libllama.0.0.5.dylib`（已追蹤原版）。

### 補洞 1（漏 commit）
- nested commit `1882f8a`：把 build/bin 的 10 個 M 檔 + `.gitignore` 入庫。
- ROOT commit `78c8678`：追蹤 `0.0.17` 三個 dylib + `.gitignore` carve-out。

### 補洞 2（沒追蹤）
- 兩邊 `.gitignore` 都改成 carve-out 結構：
  ```gitignore
  /build*
  !/build/
  /build/*
  !/build/bin/
  !/build/bin/*
  !/build/bin/*.dylib
  !/build/bin/llama-simple
  !/build/bin/llama-speculative-simple
  !/build/bin/llama-bench
  ```
- nested 的 `0.0.15` 三 dylib、`0.0.17` 三 dylib、`.bak-nocap`/`.bak-rpath-root` 備份全部入庫。

### 防 detached HEAD
- nested 從 detached HEAD 錨定到 branch：`restore-8-26-29-85-nocap`（1882f8a）。

### 驗證
- otool：rpath/chain 全部指回 nested roadB build/bin ✓
- run（qwen36 35B）：**無 `n_batch capped` 訊息** → 無 cap dylib 鏈生效 ✓
- run 因 GPU Metal working set OOM 無法原地重測 29.85 t/s（環境限制，見疏失 G）。

## 5. 防護措施 / 今後 SOP

1. **Build 完成即 commit**
   每次 build 出 working binary 後，`git add` 所有 dylib/exe/script 並**立即 commit**，message 標註日期 + t/s。離開 session 前先 `git status --short` 確認無殘留。

2. **ignore 策略不再一刀切**
   build 產物用 carve-out 保留關鍵檔；任何新產物先 `git check-ignore <file>` 確認沒被吞掉。

3. **一律在命名 branch 上工作**
   開工前 `git status -sb` 確認非 detached；若在 detached，先 `git checkout -b <描述性branch>`。

4. **Golden artifact 對照表**
   把 29.85 t/s 的 dylib 集合 + `shasum` 記在 `scripts/`（或本報告），並提供驗證 script 檢查 production exe 的 rpath、dylib 目標與哈希是否等於 golden。

5. **rpath / symlink 改動視同 code**
   任何 `install_name_tool` / `ln -s` 改動必須同步 commit 或寫 changelog；禁止只改不記。

6. **定期掃描「該追蹤卻被忽略」**
   定期跑 `git status --ignored --short`，比對是否有 build/bin 的關鍵產物被靜默忽略。

7. **環境警戒**
   16GB 機器跑 35B 全 offload 在 Metal working set 臨界點。重測 29.85 t/s 前：關閉 GPU-heavy app（Doubao 等）、確認無 swap/壓縮記憶體滿載、必要時重開機。OOM 屬硬體限制，不是 code 回歸。

---

## 6. 結論

這次事故的本質是**「產物紀律」的全面失守**：做了效能最好的 build 卻沒 commit、該追蹤的被 ignore、在 detached HEAD 上亂跳、改 rpath/symlink 不留紀錄。git 不是壞了，而是我們從沒讓它看到這些關鍵檔案。

已把「漏 commit」與「沒追蹤」兩個洞補上，並錨定到命名 branch；後續靠第 5 節的 SOP 防止再犯。29.85 t/s 的重測需要乾淨 GPU 環境，屬硬體/環境限制而非本次疏失所致。

- 修復歷史需改寫 `30988f1`/`f810fa5` 的 tree（注入 dylib blob）並 rebase 後續 commit，風險高且該 restore branch 未推送，HEAD `1882f8a` 已完整可重現 29.85。
- 此處僅記錄已知洞；「checkout 任一 commit 都自足可 build」不列入目標。
- 真正的防線是 pre-commit 檢查（`scripts/check_build_tracked.sh`）+ 第 5 節 SOP，防止「未來」再製造此類 commit。
